# Dispatch Pilot：一轮中途在事件上换 effort：追加一行输入让新档生效，判断交给决策模型，升降写在代码里

2026-11-10 用户的决定：「按照 jev 和 liquid 的最新文档指南，将中途换档全面落地，一定确保判断准确并让 agent 提高效率」；「计划获批后降一档去实现」不做。背景是 agent 现在常跑几十到几百步的任务，而 0.9.0（ADR 0013）之后一轮的 effort 只在发消息时定一次。

两份调研是这次决定的依据：`docs/research/effort-switch-timing.md`（什么时候换）和 `docs/research/decision-models-midrun-judgment.md`（怎么问、怎么读）。

## 引擎上能不能换（2026-11-10，Claude Code 2.1.322，临时探针 mod，读会话记录里每条助手消息实际生效的 `effort`）

- `turn.step` 在只带工具结果的一步上改等级，仍不生效（主 agent 和派出 agent 一样，升降都不行），和 ADR 0013 测的一致。数字 effort 被引擎拒绝。
- 在 `tool.call` 的 hook 里、`next(e)` 返回之后调 `$.session.append({ message: { type: 'user', content: [一个 text 块] } })`，下一步就算带输入的一步：那一步写的等级生效，并保持到之后只带工具结果的各步。Sonnet 5.5、Opus 5.5、Fable 5.2、Haiku 5.5 的主 agent 都测过；带 `agentId` 追加到派出 agent 的对话，Sonnet 和 Haiku 测过。这一行在请求里排在这一步所有 `tool_result` 之后，一步并行几个工具调用时也一样；会话记录里它是 `isMeta` 的 user 行，用户看不到它被当作输入。文字包在 `<system-reminder>` 里同样生效。prompt cache 不受影响。
- 在 `turn.step` 里追加，晚一步才生效。
- 本来就带输入的步不用追加：一轮进行中送进来的后台任务通知和 agent 交回（`prompt.submit` 带 `turnId`），以及 Stop hook 的反馈之后的那一步（同一个 `turnId` 接着走，前一步没有工具调用）。
- 交互界面（tmux 里的一个交互会话，同一天）：两次追加的行都没有显示在屏幕上，会话记录里有它们（`isMeta: true`），实际生效的档 high → xhigh → high。
- 没测：Workflow 里的 agent 能不能追加。

## 决定

- **只在事件上判，不定时。** 0.8.x 每隔几步重判，评测里该保持的回答有 30% 被改了档。本机 16 天的会话记录（约 2.4 万步）里，思考多的步并不成串（这一步重、下一步也重的概率 22%，基准 17%），按步数或时间猜不出难度。事件有这几种（`decision/midrun-track.ts`）：
  - **失败复现**：同一类命令在改过文件之后又失败；原先通过的命令改过之后失败；下一个失败的步报了同一条首行。单独一次失败不算（本机记录里报错的步 59% 不思考，多数是被 hook 拦下、命令写错）。被 hook 或用户拒绝的调用不算失败。命令是 shell 命令（按它真正运行的那一段的前四个词归类，选项不算），或 MCP server 的工具（按工具名）；用 shell 写文件也算改过文件。
  - **加载 skill**、**派出的 agent 或 Workflow 随调用交回结果**（调用运行了 5 秒以上，而且结果不是启动确认：这一版引擎上派出几乎都是后台启动，结果之后作为报告送进来）、**任务清单换到下一项**（`TodoWrite`、`TaskUpdate`，或宿主的计划工具）。
  - **送进这一轮的报告**（后台任务通知、agent 交回）。
  - **升档所为的那条命令重新通过**：代码自己把档位收回，不问决策模型。
- **怎么换。** 要换档时，在那次工具调用结束时追加一行（`<system-reminder>`，一句话写从哪一档到哪一档、为什么，注明不用回应），再把这一轮计划里的 effort 改掉，核心照常在每一步写它。追加失败就不改计划：只带工具结果的一步上写的档发不出去，看板不能写一个模型没在用的档（ADR 0013 的教训）。本来就带输入的步不追加。
- **怎么问**（`decision/midrun.ts`，一个请求）。按 TypeSafe 的指南「判断交给模型，决定写在代码里」，不问「该不该升档」，也不问「比现在这一档多吗」：
  - `midrun.level`：一道绝对档位的 Score，问 `recent_steps` 还没做的那部分工作需要多少逐步推理，五档的描述和发消息时一字不差。题面不提当前档，也不预设「剩下的工作」，「还在进行」写在 state 的 `progress_note` 里。
  - 几道可观察信号的是非题，「是」和「否」都写成具体情形：`cause_unknown`（最近的失败原因还没找到；助手在调用之前说过会失败、或它的文字点明了原因，是「否」）、`env_failure`（失败来自环境：超时、限速、缺程序、凭证过期、被拒绝）、`new_ground`（发现了任务没写到的工作）、`mechanical_rest`（剩下的只是照做）、三道出错代价（问「还没做的工作」），以及只在有两条报错可比时才问的 `same_failure`（两条报错放在这道题自己的 instructions 里）。
  - state 只有几千 token（上限 4000）：`task`（这一轮的消息）、`standing_constraints`（有才发）、`progress_note`（一句话说明这份 state 怎么读）、`recent_steps`（最近 8 步，从早到晚；每步是助手文字的结尾和各个工具调用的对象、成败、失败时的首条出错行；工具返回的内容不发）、`facts`（代码数出来的事实句）、`report` 或 `next_item`（有才发）。不放当前档，不放判断过几次。
- **怎么读**（`decideMidrun`，每一步都记进推演，ADR 0004）。
  - 基础档：位置四舍五入；Jev 的双峰照旧上取一档。回答拿不准时保持现在的档：发消息时 Liquid 的「置信度低于 0.5 上取一档」在这里不用，一轮进行中有发消息时没有的东西，就是现在这一档。
  - 读当前档两侧各档概率的合计，不拿置信度当升降的门槛（TypeSafe 的 Confidence 页）。门槛按决策模型各自的指南（`decision/guides.ts` 的 `MIDRUN_BARS`）：Jev 升档一侧 ≥ 0.3、降档一侧 ≥ 0.7、置信度低于 0.5 不降；Liquid 是 > 0.2、> 0.8、0.5。升和降用不同的门槛，是因为降错的代价（返工）比升错大。
  - 红旗取最高、不取平均：出错代价里「难以挽回」和「线上或权限」同时为是，至少 xhigh，只有一道为是，至少 high（发消息时的规则各低一档，和中途的上限一样）；失败复现时原因未知为是而且不是环境故障，low、medium 升到 high，已经在 high 以上的要这一轮此前已有一次这样的失败才再升一档；拿不准时至少 high。
  - 读数升档：基础档高于当前档而且高的一侧够门槛。到 high 可以一步到位，high 以上一次一档。失败来自环境时不按读数升（多想修不好一个挂掉的服务）。一轮中途最高到 xhigh，max 只留给发消息时的规则和用户的话。
  - 回到原档：升过档、读数不高于发消息时的档、低的一侧够门槛、回答已经集中、没有红旗。为失败升的档由代码在命令重新通过后收回（升档后至少过 4 步；本来就带输入的步上是 3 步）：收回到发消息时的档，这一轮出错代价要过更高的档时只收回到那一档（记在这一轮记录的 `stakesFloor`）。之后又在别的事件上为读数或出错代价升过，就不由代码收回，等之后的事件读出来。
  - 降一档（比发消息时低一档，开关 `midrun-down`）：只在不是失败的事件上，而且 `mechanical_rest` 为是、`new_ground` 为否、读数低于当前档、低的一侧够门槛、回答已经集中，这一轮没出过红旗，也不低于发消息时的规则下限（R1 到 R5、确认、要求升级里最高的那个，记在这一轮记录的 `ruleFloor`）。两道题缺一个回答、或回答没有置信度，就不降。
  - 防抖：每轮追加换档最多 4 次，最后一次只留给升档（升不上去比多想一档糟），两次之间至少隔 4 步（红旗的升档不等这 4 步）；不追加的换档不受这两条限制。每轮最多问 12 次，两次之间至少隔 4 步，改过又失败和同一条报错不等这 4 步（原先通过、改过之后失败要等：先写测试再实现时每隔几步就红一次）；追加用完之后不带输入的步上不再问；同一时刻一轮只有一个请求、只有一个调用去追加。
- **锁定、失败和关着时。** `/dp lock` 锁住的一轮不问也不换；模型不接受 effort、没配决策模型时也不问。请求失败或超时，这一步沿用原档，看板记一条。`/dp midrun-effort off` 关掉整项功能。
- **派出的 agent：先升 effort，再升模型。** 派出 agent 计入的失败第一次到 `escalateAfter` 时，把它的 effort 升一档（最高到 xhigh），用带 `agentId` 的追加行让它生效，不问决策模型；之后再到门槛才像以前那样升模型（升 effort 的那一步里再到门槛不算，新档还没用过）。Anthropic 的建议是先升 effort 再换模型，换模型还会让这个 agent 的缓存作废。用户点名了 effort 的 agent、Workflow 里的 agent（不在 `$.agent.list()` 里）、`midrun-effort` 关着时，照旧直接升模型。追加不成也照旧升模型。
- **不做的。** 定时重判；收尾、写汇报前降档（effort 几乎不改回复长短，低档更容易提前停）；高风险动作之前换档（调用已经发出，最早只能影响下一步）；按 hook 拦截、用户拒绝、零散报错升档；一轮中途升到 max；Workflow 里的 agent 中途换档；计划获批后降一档（用户的决定，和 ADR 0016 的「确认至少沿用上一轮的档」一致）；Stop hook 反馈的那一步上问决策模型（那一步只用来不花追加行地收回欠着的档）。

## 评测和审查之后改的（同一天）

评测集 `effort-midrun`（122 题：0.8.x 的 100 题转成新输入，加 22 道新情形；`dispatch-pilot/eval/datasets/README.md`），请求和读法都用 mod 自己的函数，评分的是 `decideMidrun` 发出的档。Jev 当天没测（环境里的 TypeSafe key 被拒绝），换了 key 之后只跑了改后的规则。第一次的结果：d1-ultra 71.9% / 72.7%（中文 / 英文），d1.1 71.9% / 71.6%，每题都保持现在的档 54.1%；该保持的 51 题有三成被动了。错在四处，都改了：

- `cause_unknown` 对预告过的红灯、已经点明原因的失败也答是（48 个回答里 47 个被抬高）。判据的「否」补上这两种情形。
- 环境的失败被 Score 的读数抬高。失败来自环境时不按读数升。
- Liquid 的「置信度低于 0.5 上取一档」在中途把该保持的题抬高。中途不用它。
- 出错代价一道为是就到 xhigh，误报多于命中（d1-ultra 丢 14 个得 2 个，d1.1 丢 19 个得 13 个）。改成两级。

改完重跑：d1-ultra 78.4% / 79.0%，d1.1 76.8% / 75.7%；该保持的题 93% 和 88% 对，被动了的降到 11–19%；失败事件 16 题从 38–58% 到 73–85%。**这些改动是看过这套题之后做的，没有留出的题**，新数字只说明方向。该降的 34 题仍只对 45–49%（Score 自己没读低、一次只降一档）；降一档这一条在这套题上值 2.7 和 3.9 个百分点，把题降到所有可接受的档以下的回答是 732 个里的 6 个和 3 个。Jev（换了 key 之后补跑，`jev-latest` 由 jev-1.14.0 应答，TypeSafe 的读法，只有改后的规则，没有改前的对照）79.0% / 78.1%：该保持的题 93% / 91% 对，失败事件 81% / 71%，该降的 50% / 53%；单发的中位 262 毫秒，732 个回答没有一个超过 `timeoutMs`；降一档值 3.7 个百分点，降错的也是 6 个。数字和读法见 `dispatch-pilot/DEVELOPMENT.md`「一轮中途的 effort（effort-midrun，ADR 0020）」。

一次独立的代码审查找出的缺陷也改了：同一步里一起结束的几个调用各追加一行（现在只有一个去追加）；命令重新通过时把后来为出错代价升的档一起收回（先改成出错代价为是就不收回，Jev 的真实会话之后改成只收回到出错代价要的那一档，见下）；刚派出 agent 被当成交回；任务清单只认 `TodoWrite`；通用的首行（`Traceback …`）被当成同一条报错；`pnpm --filter api test` 和 `… build` 归成一类；派出 agent 一步里失败到两次门槛时 effort 和模型一起升；state 在约束很长或一步调用很多时超过 4000 token。

Jev 的真实会话（换了 key 之后，Claude Code 2.1.322，Sonnet 5.5，`claude -p`，一条要改四次才通过的测试命令，三次）：中途的请求 255–335 毫秒回来，答题的是 jev-1.14.0。一次发消息时定在 low，第二次失败升到 high、第三次升到 xhigh；一次定在 high，第三次失败升到 xhigh，命令通过后收回到 high；每次换档各追加一行。第一种里先抬到 high 的是出错代价，按当时的写法（出错代价为是就不由代码收回），为失败再升的 xhigh 在命令通过后留到了这一轮结束。改成记下这一轮出错代价要过的最高一档（`stakesFloor`），命令通过后收回到它和发消息时的档里较高的一个：出错代价要的档不动，为失败多升的收回。

## 考虑过的其他做法

- **先只观察、不换档，定好门槛再打开。** 调研里的建议。用户选直接落地，门槛用两家文档里的起始值。
- **先让 Haiku 把轨迹压成摘要再判。** 两家都没有这种官方模式；TypeSafe 自己的评测里读 agent 轨迹，Jev 是 71.6%、0.5 秒，Haiku 4.5 是 57.2%、7.1 秒（厂商自测）。它会把一次判断的成本和延迟抬到决策请求本身的几十倍。
- **相对题**（「比当前档需要更多推理吗」）。Score 的每一档单独评，模型看不到档位名；相对题是多跳，TypeSafe 把它列为失准的原因。
- **中止这一轮再提交一条续做的消息**（`$.turn.abort` 加 `$.prompt.submit`）。能换档，但打断正在进行的步，比追加一行重。
- **`$.session.send` 给运行中的 agent 发消息。** 也能造出带输入的一步，但它是一条真的消息，会被当作要回应的内容。
- **只按计数升档，不问决策模型。** 本机记录里代码能认出的「同一类命令改过又失败」每 5,000 步才一次，按首行认又混着通用的末行；失败来自环境时多想也没用，这要读内容才分得出。派出 agent 的那一次升 effort 仍只按计数：它替换的是原来按同一个计数升模型的那一次，比原来轻。

## 代价

- 每次换档在对话里多一行模型读得到的提示。Anthropic 的指南提醒 harness 插话太勤会被读成注入，所以每轮最多 4 次；长任务里多次追加的效果没有对照实测。
- 事件上多一次决策请求：Jev 一次约 0.3–0.5 秒，d1-ultra 实测 0.35–0.63 秒（几百 token 的 state），都发生在那次工具调用结束时，结果晚这么久交给模型。
- 没有任务清单、没有失败复现、没有报告和 skill 的长循环里不会有事件，档位就是发消息时定的那一档。
- 派出 agent 第一次到失败门槛时不再换模型，要再失败到门槛才换。
- 降一档仍可能判错；它只降一档、只在读数和两道是非题都同意时才降，`/dp midrun-down off` 可以单独关掉。
- 门槛是两家文档的起始值，没有在我们的评测上调过（ADR 0014 的做法）；规则的四处改动是看过 `effort-midrun` 的结果之后做的，没有留出的题。Jev 只跑过改后的规则，没有改前的对照。
- 一个 MCP 工具反复因为同一行报错失败（例如抓网页被拒）也会问一次；`env_failure` 为是时不升。
- 2.1.322 之前的引擎没有测过；追加不了时不换档，其余功能不受影响。

版本 0.11.0。取代 ADR 0013 里「一轮的 effort 只在发消息时定」和「派出 agent 失败时只换模型」两条；ADR 0013 的实测结论（只带工具结果的一步上改 effort 不生效）仍然成立，正是这次做法的前提。

后来被 ADR 0022（2026-11-11，0.11.0） 改了（用户的决定：主 agent 和派出的 agent 都可以升到 max，不设上限）：一轮中途不再有「最高到 xhigh」，「一轮中途升到 max」也从「不做的」里去掉。读数升档到 high 一步到位、high 以上一次一档，可以到 max；失败复现且原因未知，已在 high 以上、这一轮此前已有一次这样的失败时再升一档，可以到 max。出错代价两道同为是仍是至少 xhigh、只有一道为是至少 high：离线重判里两道同为是给 max 在 d1-ultra 和 d1.1 上都低 1.6 个百分点，Jev 上没有差别（79.4 对 79.1）。派出 agent 失败时先升的那一档 effort 最高到 max。Liquid 的基础档现在在发消息时也按回答本身读，`MidrunBars.unsure` 删了；三道出错代价的判据随发消息时的一起改细。回到原档、降一档、防抖和 `stakesFloor` 不变。

# Dispatch Pilot：发消息时的 effort 按评测重定：是非题的判据、两条下限的档位、档位描述、Liquid 的读法；一轮中途和派出 agent 都可以到 max

用户 2026-11-11 的两个决定：

1. 「发消息时的 effort 这个也需要做新的，跟着你但是做 mid-turn 同样严格的标准，来确保 decision 模型的判断准确。」
2. 「主 agent 和派出去的 agent 都可以通过 decision model 的判断升到 max 档位，不要限制。所以对于这一点是否还需要调整 decision 问题，结合相关最新文档评估然后更新。」

「同样严格的标准」照 ADR 0020 的做法：用 mod 自己的请求和规则在三个决策模型上各跑三遍，逐条看错在哪条规则，改题面和规则，重跑，独立审查，真实会话验证。

## 基线：0.9.0 的规则在三个决策模型上（2026-11-11）

`effort-submit`（100 题，中英各一遍，每题 3 次，变体 `en-score`，就是 mod 发的请求；回答按答题模型自己的指南读）：

| 决策模型 | 准确率（中文 / 英文） | 判高 / 判低（600 个回答） |
|---|---|---|
| Jev（jev-1.14.0） | 78.0% / 77.3% | 128 / 6 |
| d1-ultra | 66.3% / 66.7% | 201 / 0 |
| d1.1 | 61.3% / 67.7% | 213 / 0 |

`subagent`（100 题，`nouls`，Jev）：模型和 effort 都对 42% / 43%，模型 64% / 66%，effort 46% / 45%。

错的几乎全是判高，来源有四处：

- **两条下限的档位太高。** Jev 只看 effort 题自己的读数是 92% / 88% 对；出错代价这条下限抬了 32 个回答，17 个从对抬成错、2 个从错抬成对，原因未知抬了 10 个、9 个抬成错（一次运行的 200 个回答）。任一出错代价为是就到 xhigh、拿不准就到 high，原因未知为是到 xhigh，是 ADR 0014 定的起始值，没有量过。
- **是非题把不算数的情形也答成是。** 「看一眼 `.env.production` 里的超时配了多少」「把 `config/prod.yaml` 的日志级别改一下」线上为是（0.72–0.86）；「drop 掉测试库里那张临时表」难以挽回为是；「review 一下登录接口的参数校验」权限为是（0.92）；「写个 GitHub Actions 推镜像发 release」难以挽回和权限同为是，定到 max；「用 git bisect 找出是哪个 commit」原因未知为是（0.99）。
- **Liquid 的「置信度低于 0.5 上取一档」。** 同样的回答只按位置四舍五入读，d1-ultra 是 83.7% / 81.7%，d1.1 是 90.0% / 90.3%（不带下限）；带上这一条是 70.7% / 70.3% 和 72.3% / 73.7%。它是 ADR 0017 从 Liquid 的路由示例借来的，Liquid 的指南没写打分题拿不准怎么办；ADR 0020 在一轮中途已经因为同样的原因不用它。
- **档位描述和标注的档位表对不上。** 评测集的档位表（`dispatch-pilot/eval/datasets/README.md`）写 medium 是「范围清楚的单点改动或解释」、max 是「安全审计、证明、疑难并发问题」，审核规则写「写测试按范围定档」；effort 题的描述里解释没有位置，「writing tests」整个放在 high，「a security or data-integrity question」放在 max。用文字解释架构、并发、安全话题的消息，回答分成 low 和 xhigh / max 两头。

## 决定

- **两条下限的档位**（`decision/message-effort.ts` 的 `stakesFloor`、`causeFloor`，派出 agent 共用）：难以挽回为是而且线上或权限为是，max（不变）；任何一道为是，至少 high（原来 xhigh）；原因未知为是，至少 high（原来 xhigh）；拿不准不再抬（原来 high）。effort 题自己的档位描述里已经有「原因未知的 bug」这一档，难的它自己会读高；要靠下限抬过低读数的只有「难以挽回而且线上」这一种（「好，执行吧」批准一次生产库的合并，读数是 medium）。
- **四道是非题的判据写细**（`decision/effort.ts` 的 `NOULS`，一轮中途的三道出错代价经 `stakeSituations` 共用；派出 agent 的在 `decision/dispatched-agent.ts`）：难以挽回的「是」限定为助手自己在这项工作里删除或覆盖还有用的数据（改写别人也在用的 git 历史也算）、向外发送、发布或部署，「否」加上以后有人运行才生效的代码、配置、流水线，审查，和删掉用完即弃的东西；线上的「是」限定为助手自己改动线上的东西或动真钱，「否」加上只从生产环境读、只改之后由别人应用的文件；权限的「否」写明阅读、审查、解释和访问有关的代码、使用已配好的凭证都不算；原因未知的「否」加上用户只要一个定好的步骤而没问原因。TypeSafe 的指南要求每道是非题的「是」「否」写成具体情形，这是把缺的情形补上。
- **五档描述对齐档位表**（`LEVELS`，发消息、派出 agent、一轮中途共用）：low 是凭已知信息的简短回答或机械工作；medium 加上用文字给出的解释或建议（不论话题）和给一小段代码写用例已给定的测试；high 加上在文件之间搬动或拆分代码、用例或准备工作要想清楚的测试、仔细审查一小段代码；xhigh 的重构限定为改变很多依赖方所依赖的行为或接口的；max 的安全一项改成对一整套机制的安全或数据完整性做审计。档位表写明 `effort.ts` 的描述是被测的提示词。
- **Liquid 的 effort 题按回答本身读**（`LIQUID_GUIDE.scoreUnsure` 改成 `none`）：发消息时、派出 agent、一轮中途都一样；`ScoreUnsure` 的 `low-confidence` 和 `MidrunBars.unsure` 删了。派出 agent 选模型的路由仍照 Liquid 的示例，置信度低于 0.5 退到最强。Jev 的双峰规则留着：去掉它在这套题上只多对 1 题左右，在运行之间的波动之内，而它是 TypeSafe 文档自己的提醒。
- **一轮中途不设上限**（`MIDRUN_CAP` 删了）：读数升档到 high 一步到位，high 以上一次一档，可以到 max；失败复现而且原因未知，已在 high 以上、这一轮此前已有一次这样的失败时再升一档，可以到 max。已存的回答离线重判，上限从 xhigh 放到 max，三个模型都略好（Jev 78.6 → 79.4，d1-ultra 78.7 → 79.5，d1.1 76.2 → 76.6）。出错代价两道同为是仍是至少 xhigh：改成 max 时 d1-ultra 79.5 → 77.9、d1.1 76.6 → 75.0、Jev 79.4 → 79.1。原因未知拿不准时至少 high 也留着：去掉它准确率多 0–0.6 个百分点，判低的回答却从 22–27 个多到 28–34 个。
- **派出 agent：模型表第 ③b 行不再给 max。** 七道题没有为是、有拿不准的，仍给 sonnet，effort 就是基础档加下限。原来这一行把 effort 抬到 max（ADR 0015：拿不准时用 sonnet 加 max 代替 opus）；下限改完之后的那次运行里，模型判对、effort 判错的 40 个回答有 22 个在这一行，其中 19 个的基础档本来是对的。Anthropic 的 effort 文档（2026-11-11 读的）：max 留给「the rare task where time and tokens don't matter」，「often for only a small gain」；Sonnet 5.5 和 Haiku 5.5 的 xhigh、max「only where your evals show a quality gain」；low 的典型用途里写着「such as subagents」。拿不准不是把 agent 放到 max 的理由。
- **派出 agent 失败时先升的 effort 最高到 max**（`effortUp`，原来 xhigh）。
- **max 从哪里来**：effort 题自己的读数到最高一档（发消息时、派出时、一轮中途）；难以挽回而且线上或权限同为是（发消息时、派出时）；同一个问题连着没解决满 `unresolvedMaxAfter` 次（R5）；一轮中途同一类失败连着复现；派出 agent 失败满门槛；用户点名。
- **问题要不要为 max 另改**：不用另加题。发消息时 gold 是 max 的 8 题，Jev 的读数或「难以挽回而且线上」的下限都到了可接受的档；一轮中途放开上限之后该升的题多对 1–3 个百分点。改的是上面那几处判据和描述。

## 结果（同一天，同样的跑法，每题 3 次）

`effort-submit`：

| 决策模型 | 改之前 | 改之后 | 判高 / 判低（600 个回答） |
|---|---|---|---|
| Jev | 78.0% / 77.3% | 97.0% / 94.7% | 128 / 6 → 16 / 9 |
| d1-ultra | 66.3% / 66.7% | 90.7% / 89.3% | 201 / 0 → 58 / 2 |
| d1.1 | 61.3% / 67.7% | 92.7% / 91.7% | 213 / 0 → 39 / 8 |

改之后两条下限在 Jev 上净多对 1 个百分点（出错代价抬的 12 个回答都是从错抬成对，原因未知抬的 6 个都抬成错，是 git bisect 那一题），判低的回答从 21 个减到 9 个。

`effort-midrun`（题面和上限改了之后重跑；ADR 0020 的数是 79.0% / 78.1%、78.4% / 79.0%、76.8% / 75.7%）：Jev 79.2% / 78.7%，d1-ultra 78.1% / 78.7%，d1.1 77.9% / 75.4%，都在运行之间的波动之内。

`subagent`（`nouls`，1 次）：Jev 模型和 effort 都对 42% / 43% → 58% / 56%，effort 46% / 45% → 67% / 65%，模型 64% / 66% → 65% / 64%（模型表没动）。d1.1 第一次跑：67% / 63%，模型 72% / 71%，effort 72% / 71%。

**这些改动是看过这三套题之后做的，没有留出的题**：判据和描述是对着错题写的，新数字只说明方向对，别处的准确率会低一些，低多少没有量。

## 考虑过的其他做法

- **只留「难以挽回而且线上」一条下限，单道出错代价和原因未知都不抬。** 题面改之前这样最高（Jev 92.0% / 87.7%）；题面改细之后两种做法差不到 1 个百分点，留着单道到 high 的判低更少。
- **去掉 Jev 的双峰规则。** 见上，差别在波动之内。
- **回答分成两头时另问一道「这是不是只要用文字回答」。** 能多对两三题；改了档位描述之后这几题不再分成两头，不需要。
- **一轮中途出错代价两道同为是也给 max，和发消息时一样。** 离线重判更差（见上）。
- **第 ③b 行改成至少 high。** 离线重判 effort 对 107 / 189，不给下限是 110 / 189。
- **派出 agent 也在事件上问决策模型换档。** 没做：派出 agent 中途仍只按失败计数升（ADR 0020）。

## 代价

- 判据和描述是对着这三套题调的（见上）。
- 单道出错代价从 xhigh 降到 high、原因未知从 xhigh 降到 high：真有风险而读数又低的消息现在少一档。评测集里这样的题只有「难以挽回而且线上」那一类，它仍是 max。
- Liquid 的回答拿不准时不再上取一档：d1.1 判低的回答从 0 个到 8 个（600 个里）。
- 一轮中途同一条命令连着失败三次、每次都读成原因未知，会从 low 或 medium 一路升到 max（真实会话里见过：low → high → xhigh → max，命令通过后收回）。Anthropic 的文章说更高的 effort 治不了方向错；这是用户要的不设上限。
- 派出 agent 的模型仍只对 65% 左右，判高为主（200 个回答里，该用 haiku 的有 47 个给了 sonnet、opus 或 fable）：模型表（ADR 0015）这次没有动。
- 判据和档位描述变长，每个发消息的 effort 请求多约 230 token（Jev 计，2147 → 2373）。

## 验证（2026-11-11）

- `scripts/check.sh dispatch-pilot` 通过。
- 评测结果在 `dispatch-pilot/eval/results/`：`effort-submit/2026-11-11-{jev,d1,d1.1}-base-x3.json`（改之前）和 `-rules3-x3.json`（改之后），`effort-midrun/2026-11-11-{jev,d1,d1.1}-mod-x3-rules4.json`，`subagent/2026-11-11-jev-v0110.json`（改之前）、`-jev-rules3.json`、`-d1.1-rules3.json`；中间几轮（`-crit1`、`-rules2-x3`、`-lv1`、`-lv2`、`-mod-x3-rules3`）也留着。这一轮共约 1.3 万个请求，约 1.05 美元。`eval/lib/effort-submit.ts` 改成按答题模型自己的指南读回答（原来一律按 TypeSafe 的线），并记下每道是非题的回答，离线重判不用再发请求。
- 真实会话（Claude Code 2.1.322，Sonnet 5.5，决策模型 Jev，`claude -p`）：「线上告警在响，看一眼 `.env.production` 里 `API_TIMEOUT` 配的多少」定在 low；一条要改几次才通过的测试命令，low → high → xhigh → max 各追加一行，命令通过后用这一轮的第四行回到 low，之后的步都在 low（审查的修复之后跑的；修复之前的一次是 medium → high → xhigh → max，要等到一个带输入的步才回到 medium）。
- 一次独立的代码审查找出的缺陷都改了（清单见 DEVELOPMENT.md「发消息时的 effort 重定」一节）。和不设上限直接相关的一条：连升三档到 max 之后，这一轮最后一次追加原来只留给升档，max 上没有可升的，命令通过也收不回来；改成在 max 上往回也可以用最后一次。一轮进行中用户又发一条消息时，这一轮此前记下的出错代价的档、棘轮和待收回的升档也清掉。

版本 0.11.0（和 ADR 0020、ADR 0021 同一个版本）。改了 ADR 0014（R2、R3 的档位，Liquid 之外的读法不变）、ADR 0015（第 ③b 行的 max）、ADR 0017（Liquid 的 effort 题拿不准时上取一档）和 ADR 0020（一轮中途最高到 xhigh、派出 agent 的 effort 最高升到 xhigh）。

# Dispatch Pilot：Jev 用长上下文读对话，一起派出的 agent 合进一个请求

Jev 1.14 的长上下文请求头（`TypeSafe-Danger-Zone-Long-Context`）让一个请求到 262k token，不带时是 64k，state 加一道题 32k。用户要求开启长上下文，但不占满：取窗口的 40%–60%。派出 agent 和 Workflow 里的 agent 一起改：合进一个请求判断，太长就分几个合并请求；能并行，但不超出最佳性能范围；判断时带上 Haiku 5.5 写的问题摘要。同一天用户给了 TypeSafe 账号的限额（默认套餐：每秒 80 个请求、10 万 input token），要求按它调整并发。

决定：

- **96000 估算 token，超过 24000 才带请求头。** 用在发消息时主 agent 的 effort 题、派出 agent、Workflow 里的 agent。按 Jev 的计数约 11.5 万到 13.2 万，是窗口的 44%–50%。其余请求一字不改。
  - 依据：一段长对话的 30 道题（ctx30），长上下文对 25 道，只读最近 24000 对 13 道（p = 0.0005）。
  - eval v2 整段读到平均 14.6 万（56%）时，并不比 24000 好。
  - 官方文档说长上下文比留在常规限制里慢、不那么准。
- **中途重判不变，24000，不带请求头。** 它读这一轮的几步，加上你的消息和问题摘要，一般几千 token。步骤只等它 300 毫秒，而一个长请求要 1–1.5 秒。
- **`contextMessages` 从 32 改成 2000。** 32 条装不满 96000。
- **等待。**
  - 带请求头的请求，以及和它一起发的请求，至少等 3000 毫秒。实测 9.6 万约 1.3–1.6 秒；额度紧时还要排队等 token（桶空了时一个满请求约 1.2 秒）。
  - 中途重判的请求本身也等 3000 毫秒，步骤仍只等 `rejudgeWaitMs`。
  - 一个 agent 最多等 6000 毫秒：它的请求，加上排在它前面的一个。
- **agent 带背景。** Jev 也带派出它的那段对话；Workflow 里的 agent 还带脚本。这改了 ADR 0007 里「选 Jev 时不带背景」。
- **一起派出、一起启动的 agent 合进一个请求。**
  - 合的范围：同一个来源（同一个 loop，或同一次 Workflow 运行）的 agent。
  - 共享的内容只放一份：你的话、问题摘要和次数、对话、脚本。
  - 每个 agent 各占一个字段，各问各的题。一个请求最多 8 个。
  - 同一条消息的 Agent 调用都到了才发，最多等 300 毫秒。Workflow 的 agent 等各自的任务读到。
  - 之后才启动的 agent 进下一个请求：Workflow 的 agent 不是一次生成的。
- **车道。** 关于 agent 的请求同时在途有上限：Jev 4，pplx 5。车道占满时，新到的 agent 并进还没发的那个请求。
  - Jev 取 4 的依据：同一天实测，4 个约 11.5 万 token 的长请求同时发，各 1.39–1.53 秒答完，单发一个 1.44 秒，没有 429。5 个以上没有试。
  - 起初定为 1，依据是 1.13 上短请求的实测（同一个 key 的请求像是依次处理）；这对 1.14 不成立。
  - Workflow 提交时拼好的几个请求也走车道。
- **按账号限额给 Jev 限速**（`decision/jev-rate.ts`）。所有 Jev 请求都经过它，评测不经过。
  - 两个选项：`jevQps`（默认 80）、`jevTokensPerSecond`（默认 100000），填控制台上的数。
  - token 用令牌桶：最多存 5 秒的额度（默认 50 万，约 4 个满请求），按每秒的额度补。请求按估算的 token（mod 的估算乘 1.3，加图）预取，答完按 Jev 报的实数多退少补。
  - effort 题排最前，其余先来先发。轮不到的请求在自己的等待时间内按超时失败，不发。
  - 429、529：所有请求按 `Retry-After` 暂停（没有就 1 秒、0.5 秒）；收到的那个请求时间够就重试一次。

代价：

- 长会话里，每条消息和每批派出的 agent 多等约 1–1.5 秒。
- 每个满的请求约 0.005 美元，以前约 0.0012。
- 额度紧时，中途重判排在长请求后面等 token，多半迟到一步。
- 准确率只有 ctx30 和 eval v2 两组数据。agent 带背景、几个合进一个请求，都没有量。
- 默认套餐下，持续的满请求约每 1.15 秒才能放出一个。长会话里一下派出很多组 agent，排在后面的可能等不到回答，按主 agent 原来的要求启动。
- TypeSafe 没写限额怎么计。桶存 5 秒是猜的，只知道一次 45 万 token 没有被限；猜多了会遇到 429，靠暂停和重试补救。
- 限速的状态在后端对象里：热重载会重建它，同一个 key 的其他会话也看不到，同样靠 429 补救。

考虑过的其他做法：

- 读满窗口（eval v2 的整段对话）：平均 14.6 万时没有变好，而且更慢。
- 中途重判也带长上下文：步骤只等 300 毫秒，长请求几乎每次都会迟到。
- agent 仍是一个 agent 一个请求、只是带上背景：每个请求都带一遍同样的对话，token 花三份，按默认套餐要占约 3.5 秒的额度。
- token 按固定时间窗算（每 5 秒 50 万）：4 个满请求之后，第 5 个要等整个窗口过去；令牌桶只等补够它缺的部分（约 0.7 秒）。
- 限速的状态放进 `$.state`（pplx 的做法）：pplx 每秒只有 5 个，多放一个就是 429；Jev 的桶有 50 万，热重载的误差小得多，不值得每个请求多读写一次。
- 按固定时间窗口攒批：每个 agent 都要多等这段时间，即使没有别的 agent 一起来。按「同一条消息的调用都到了」和「任务读到了」来合，独自派出的 agent 不等，只有等不到的调用时才最多等 300 毫秒。

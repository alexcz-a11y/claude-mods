# Dispatch Pilot：强提示另问一道 effort 题，按同一请求的三选一取用，max 门槛降到 hintThetaMax

用户在真实会话里看到：同一个问题未解决五轮以上，Jev 给 max 的概率一直很低，还会降档。重放 transcript 证实强提示发出去了，但只把 p(max) 从 0–1% 提到 1–3%：它和 effort 题的「评什么」（评请求本身的工作，不看话题多重要）冲突，Jev 按这条消息字面那一步评。

决定：

- **强提示改写。** 强提示点明这正是最高一档描述的情形，「评什么」补一句：属于多次尝试都没解决的故障时，按故障整体的难度评。仍不写档位名字和数字。
- **发消息时另问一道，不替换原题。** `effort.level` 原样，旁边加 `effort.level_unsolved`。这条消息自己的三选一判「仍未解决」时用后者，否则用前者。强提示用的是这条消息之前的次数，说「好了」「先放着，另一件事」的那条仍带强提示，靠这一步挡住。中途重判没有三选一，强提示直接加在原题上。
- **`hintThetaMax`。** 带强提示的回答，max 门槛用它（Jev 0.4，pplx 0.47 即不变），不是选项。

依据（Jev 1.14，各流程里带强提示的题）：强版直接替换原题时 long-context max 召回 1/20 → 18/20，但 eval-v2 金标不含 max 的 15 题有 13 题给了 max；弱一些的写法（「这一步简单仍按它评」）把 p(max) 压得比旧的还低。现在的做法 long-context 20/20，eval-v2 召回 7/7、金标不含 max 却给 max 9/15，多是同一个未解决问题里的简单一步。用户的决定是问题没解决期间这可以接受：问题一解决次数清零，强提示就没了。数字和结果文件见 DEVELOPMENT.md 「强提示（#41）」。

这修订了 ADR 0005 的「强提示不降 `thetaMax`」：0005 当时写明召回不够时先考虑在阈值处降 `thetaMax`。仍不设档位下限。代价：每条带强提示的消息多问一道题（同一个请求、同一份 state，几乎不加时间和花费）；pplx 没量过新写法。

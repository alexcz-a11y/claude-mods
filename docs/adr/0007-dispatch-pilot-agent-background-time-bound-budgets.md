# Dispatch Pilot：agent 的请求带上背景，pplx 的预算按回答时间定

派出 agent 和 Workflow 里 agent 的决定以前只读三样东西：主 agent 写的任务、你这一轮的话、Workflow 的 `meta.description`，而且 Workflow 的每个调用最多只给 400 token。主 agent 的对话（为什么派、计划是什么）和 Workflow 的脚本（调用之间怎么衔接、数据驱动的调用跑的是什么）都看不到。用户要求按决策模型能接受的最大 token 数，给这些请求分配上下文。

决定：

- **背景。** 选 pplx 时，派出 agent 的请求带上派出它的那段对话，到这次 Agent 调用为止，只有文字和工具名。Workflow 的请求再带上整个脚本，脱敏，最多占预算的三分之一。任务和你的话先放，背景填剩下的预算。
- **Workflow 的 brief。** 每个调用的 brief 改为平分预算，不再固定 400 token。
- **问题摘要和次数。** `unresolved` 开着时，它们也进 Workflow 的请求，不加强提示。
- **选 Jev 时不带背景。** Jev 只等 1500 毫秒，同一个 key 的请求一个一个答。请求被对话填满后，一起派出的几个 agent 大多会超时。
- **启动那一轮。** Workflow 里有些 agent 要等启动时才判断。它们读的是启动运行那一轮的东西：你那时说的话、那时的问题摘要、到那次调用为止的对话，不读之后的消息。0.4.2 及之前读的是当时的 `said`，你空闲时发的新消息会把它顶替掉。
- **预算按时间定。** pplx 一个请求最多收 262,144 token，但回答时间随长度增加，而一次决策最多等 8 秒。实测 48000 估算 token 的请求单发要 4.3–5.9 秒，72000 要 8.3–8.8 秒。因此：
  - 单个请求保持 48000：发消息时的 effort 题、中途重判、Workflow 的一个请求。
  - 派出 agent 取 32000。它们常常几个一起派，每个请求都会被对话填满。同时发 5 个 32000 的请求，都在 5.2 秒内答完；3 个 48000 的，最慢要 7.6 秒。
  - Workflow 分成几个请求同时发时、agent 启动时当场判断时，每个请求也取 32000。
  - 这条改了 ADR 0006 里「派出 agent 48000」的取值。
- **限速。** Perplexity 文档现在写每个组织每秒 10 个请求。`pplxQps` 默认从 1 改成 5，ADR 0006 里写的是 1。实测按每秒一个排队时，一起派出的第 4、5 个 agent 要 8.5 秒、10.7 秒才答完；同时发出时都在 5 秒内。

代价有两条。长会话里，每个派出的 agent 要多等 4 到 5 秒才启动。背景对准确率有多大作用没有评测，因为评测集的题里没有对话和脚本。

考虑过的其他做法：

- 预算取窗口上限，约 13 万估算 token：单发就要 20 秒以上，每次决策都会超时。
- 派出 agent 也取 48000：单发没问题，但一起派出 3 个以上时，最慢的那个贴着或超过 8 秒。
- 对 Jev 也带背景：同样预算下每个请求约 0.6 秒，一起派出的第三个 agent 就会超过 1500 毫秒。

后来被 ADR 0009 改了：选 Jev 时也带背景（对话，Workflow 再加脚本），一起派出、一起启动的 agent 合进一个请求；Jev 同时答几个长请求，「同一个 key 的请求一个一个答」对 1.14 不成立。

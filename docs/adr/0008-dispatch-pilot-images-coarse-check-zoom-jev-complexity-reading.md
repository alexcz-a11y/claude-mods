# Dispatch Pilot 的图像：看图核对只做粗筛和放大复核，带图请求走 Jev，参考图先换成复杂度读数

用户希望决策模型替 agent 看截图、视频帧和参考图，省时间和花费。用户的场景有：iOS 界面和转场动画、3D 网页特效、照参考图在网页或 Blender 里建模、画质档位的取舍。Jev 1.14 支持图像和 Box 题。2026-10-15 做了几个小实验，图是合成的，每项只跑一次，API 共花约 0.20 美元。结果显示，决策模型只能接过一部分看图的工作。

决定：

- **看图核对是粗筛，不替代 agent 看图。** 整屏判断只信粗的差异：缺元素、文字截断、大幅变色、渲染特征的有无和强弱、动画回弹、终点大偏。细微样式的差异，整屏判断会给出 72–100% 的「一致」，例如圆角 12→6、字重、4px 偏移，和完全相同的对照图分不开。只给文字规范时，色值和 pt 核对不了。「不一致」的概率很低时可信；「一致」只说明没看出明显问题。
- **有参考图或另一张截图可比时，做放大复核。** 先框出点名的部分，裁下放大，再判断。
  - 圆角的「一致」从整屏的 0.74 降到 0.10–0.15。边距和 4px 偏移落到「没把握」。字重仍然抓不到。完全相同的对照图，裁图给 0.91–0.95，没有误报。
  - 门槛：「一致」≥0.9 判过，≤0.2 判不过，中间算没把握。
  - 档位取舍依赖的是「一致」这个较弱的方向，所以每个点名的区域都要经过放大复核、达到 0.9，才算「没差别」。
- **看图核对管不到的，留给 agent。** 数值类（尺寸、圆角、pt、色值、字重）由 agent 查代码或运行时的值。观感类（缓动、质感）由 agent 自己看。交付前，主 agent 亲自看一次最终结果。
- **带图的请求优先 Jev，固定 `jev-1.14.0`。** 带图的请求指看图核对和复杂度读数；没有 Jev 密钥时退回 pplx。不带图的决策照旧跟随用户选的决策模型。
  - 这偏离了「决策模型由用户二选一」，原因是两家差得多：
    - Jev 快 2–3 倍，一个请求收 12 帧没有问题，图只计一次 token，有 Box。
    - pplx 一个请求最多 8 张图（实测，文档没写），每道题都把图重新计 token，没有 Box，做不了放大复核。
  - 代价：Jev 的图像功能官方标为 Dreamer-ready，版本之间可能变。所以固定版本号，出新版先跑评测再换。
- **带图路由先把参考图换成复杂度读数。**
  - 单独问一道复杂度打分题，同一组参考图只问一次。
  - 读数以文字进入以下决定，只作提示：主 agent 的 effort，派出 agent（含 Workflow 里的）的模型和 effort。
  - 这样做的依据：mod 现有的 effort 题带上图后对图不敏感，Jev 对三组参考图都答 medium；单独的复杂度题，两家都排对了顺序。
  - 同一个请求里，题和题之间看不到彼此的答案，所以读数和 effort 要分成先后两个请求。带图的消息，第一步因此多等约 0.5–1.5 秒。

考虑过的其他做法：

- 让决策模型完全替代 agent 看图：细节会大量漏判，而「一致」又不可信，错判会一路留到用户验收。
- 把图直接放进每个决策请求：effort 题对图不敏感；选 pplx 时，图要按题数重新计 token，Workflow 成批的请求会被拖慢。
- 带图请求也跟随用户选的决策模型（默认 pplx）：做不了放大复核，多帧也受 8 张的限制。

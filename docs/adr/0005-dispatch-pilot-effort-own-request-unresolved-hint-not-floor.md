# Dispatch Pilot：发消息时的 effort 单独发一个决策请求，未解决次数只给决策模型强提示、不定下限

和主 agent 来回多轮都没解决同一个问题时，决策模型应当判到最高一档，但它读不到那么远：发消息时 effort 题和 skill 排序题合在一个决策请求里（投票箱），skill 排序题带着全部 skill 画像，占去 Jev「state 加最长一题」32k 上限的大半，state 只剩 6000 token。所以 effort 题从投票箱里拆出来，单独发一个决策请求（和 skill 请求并行），state 拿到和中途重判一样的 24000；投票箱其余的题照旧合发。代价是每条消息多一次 Jev 调用，延迟不变。为了看到 24000 也装不下的更早几轮，另记问题摘要（主 agent 每轮结束后在后台由便宜的模型续写，决定时从不等它）和未解决次数（决策模型逐条判断用户是否在说上次没解决）。次数达到阈值时，只在决策模型读的 state 里加一条描述情境的强提示，不写档位名字、不降 `thetaMax`、不在计划表里写下限，用不用最高一档仍由决策模型决定。考虑过的另一条路是次数到阈值就把下限抬到 max（像强制升档那样）；放弃它，是因为用户要让决策模型结合摘要和上下文自己判断，规则会盖过它。若 eval 显示强提示的召回不够，先考虑在阈值处降低 `thetaMax`，再考虑下限。

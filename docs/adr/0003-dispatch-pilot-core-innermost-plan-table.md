# Dispatch Pilot：功能分文件、核心最后注册，功能通过计划表和投票箱协作

Dispatch Pilot 的每项功能放在 `hooks/features/` 下自己的文件里，由入口按顺序注册；核心（`hooks/core/core.ts`）最后注册，所以在它参与的每个事件上都处于最内层，功能注册事件时一律带 matcher。主 agent 的 effort 和非主 agent 的 model 只由核心的 `turn.step` 写出，依据是 `$.state` 里按「轮 + agentId」记录的计划表（effort、floor、model，以及用户的 lock，优先级由 `planStep` 固定）。功能只写表，需要在某一步发出前做决定的功能就注册一层、在核心之前写表。用户发消息时，各功能把问题放进这条消息的投票箱，由核心合成一个决策请求发出，再把回答分发回去。这样安排是由 mod 的加载规则决定的：`$` 不能传过 import；同一事件不带 matcher 只能注册一次，而且这是跨文件的静态检查；同一字段上内层的改写会覆盖外层。每个字段只留一个写入者，后续十几张票才能并行开发而不必改核心。代价是功能之间的先后只能靠入口里的注册顺序，计划表各槽位的优先级也是固定的，新增优先级规则需要改 `planStep`。真实引擎上已实测：同一次 dispatch 里外层写入的 `$.state` 内层立即可读；外层 hook 的 `$` 被闭包带到内层调用时照常可用。

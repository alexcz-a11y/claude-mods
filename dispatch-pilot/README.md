# dispatch-pilot

dispatch-pilot 请 Claude 之外的一个决策模型来判断工作有多难，再由 mod 自己的规则定下主 agent 用哪一档 effort、派出的 agent 用哪个模型和哪一档 effort。决策模型默认是 Nace 的 Drex（`drex-max-v1.1`），也可以改用 TypeSafe 的 Jev（`jev-latest`）。它还收起引擎给主 agent 的完整 skill 列表，改为在你发消息时最多推荐一个合适的 skill。

主 agent 的模型从不改变，所以 prompt cache 不受影响。普通会话和 Code Mode 会话走同一套代码，行为相同。

## 它做什么

- **发消息时定 effort。** 你每发一条消息，mod 问决策模型这条消息要解决的问题有多开放（做法已经给定，还是原因不明、要做取舍），以及几道是非题（是不是照已知做法重复的改动、是不是要先查明一个原因未知的问题、是不是只是让助手接着做上一轮的事）。mod 按回答从会话设定的档位往上或往下挪，定下这一轮的档位，并由这一轮的每一步发出；消息只是让接着做、而且上一轮的档位已知时，这一轮沿用上一轮的档位，别的题都不再挪动它。只有你自己发的消息才判断，后台通知、agent 交回的报告这类开始的一轮不判断。
- **一轮中途换 effort。** 一轮进行中，mod 在检查点上再问一次：拿到最新的结果之后，剩下的工作和现在的档位还相称吗。检查点是：Code Mode 会话里每到达一份脚本结果（`midrunEveryScripts`）；普通会话里同一处报错在修改之后又出现、连续两步报错，或者每过 8 个工作步（`midrunEverySteps`）；两种会话里这一轮中途进来了新输入。要换档时，mod 在那一行工具结果后面加一行英文说明，引擎从下一次请求起发新档（见下面「Code Mode 会话里」）。一轮最多加 4 条说明（`midrunMaxNotes`），两次换档至少隔 3 个工作步（这期间到达的工具结果和脚本结果不评估，看板的「下次评估」也数到间隔过了的那一份；新输入照常评估），中途最高升到 `xhigh`，不升到 `max`。
- **派出 agent 时定模型和 effort。** 主 agent 派出一个 agent 时，mod 问决策模型这项任务的情况，最多等 3 秒（`agentTimeoutMs`），再定它的 effort，可以的时候也定它的模型。模型只往下换，而且只在把握大时才换；候选取 `agentModels` 里不高于主 agent 的那些。调用没写模型时，agent 先用它的定义里写的模型，定义没写才沿用主 agent 的，所以 mod 只给已知沿用主 agent 模型的类型定模型：每种 agent 类型在一个会话里第一次派出时，mod 不动它的模型，只记下它实际用的模型；之后再派出这个类型、主 agent 还是那一层级的模型时，记下的模型和主 agent 同一层级，才往下换或执行 `fableAgents` 的上限。定义里有自己模型的类型，模型从不改。代价是每种类型在一个会话里的第一次派出（主 agent 换了模型之后也要重新记一次）既不受上限，也不往下换。会话打开之后才改的 agent 定义里的模型，mod 要到下一个会话才会发现。`fableAgents` 关着时（默认），沿用主 agent 模型的 agent 最高到 `opus`。派出时明写了模型的不改模型，明写了 effort 的不改 effort。续跑的、fork 出来的和 Workflow 派出的 agent 不处理。
- **skill。** 主 agent 的 skill 列表换成固定的一句话，说明列表被收起、合适的 skill 会随消息推荐，其他的用 `dispatch-pilot:find-skill` 查。你发消息时，mod 按 TypeSafe 的 skill_suggestion cookbook 的两步问法最多挑出一个 skill，连同它的说明和「用 Skill 工具加载」的一句放在消息旁边；没有合适的就什么也不加。会话的第一条消息往往比第一份 skill 列表先到（实测：列表在第一次发消息之后才来），这时手里还没有候选，mod 就等这一轮里的第一份列表到了再判断这条消息，推荐接在收起列表的那句话后面；每轮最多这样补一次。主 agent 加载 `dispatch-pilot:find-skill` 并写上几个词时，mod 用同样的问法回答最多三个合适的 skill；判断请求没成（失败、超时）时，它照实说没查成，再列出会话里记下的全部候选和说明，太长时截短说明，再长只列名字（约 6000 token 以内），所以主 agent 不会比原样拿到列表时知道得更少。派出的 agent 的 skill 列表不动。
- **任何失败都放行。** 请求失败、超时、回答缺题或类型不对、Drex 回答的模型版本和 `drexModel` 不一致、模型不接受 effort，这些情况下 mod 不改档位、不改模型、不加说明，会话照没有这个 mod 时那样继续，并记一条决策记录。

用 `/dp lock <档位>` 锁定档位时，三项 effort 判断都不做，主循环的步按锁定的档位发出；`/dp unlock` 解锁。一轮进行中锁定时，这一轮里只带工具结果的步发不出新档（引擎的规矩），要到下一个带新输入的步（例如你的下一条消息）才用上锁定的档位；这之间看板如实写「要 X，实际发出 Y」。

## 要求

- Claude Code 2.1.327 及以上。
- Drex 或 Jev 的 API 密钥，至少一个。所选后端没有密钥时，mod 不发任何判断请求，skill 列表也不收起；看板和 `/dp` 里写明「没有密钥」。
- 只面向用 API key 或订阅登录的 Claude Code：按官方文档，在 Bedrock、Google Cloud 和网关上换 effort 会让 prompt cache 失效。

## 安装

```bash
claude plugin marketplace add alexcz-a11y/claude-mods
claude plugin install dispatch-pilot@alex-mods --scope user
```

装好后在 `/plugin` 里给 dispatch-pilot 填上密钥（`drexApiKey` 或 `jevApiKey`），重启 Claude Code 或运行 `/reload-plugins`。

## 配置

在 `/plugin` 里改。数值越界时按边界处理；字符串选项写了认不出的值时用默认值。

| 选项 | 默认 | 说明 |
|---|---|---|
| `enabled` | 开 | 总开关。关掉后 mod 不做任何判断，也不改任何东西：不写状态，看板不画，`/dp` 只回答 mod 关着（锁定照样能设，打开之后才起作用）。 |
| `board` | 开 | 时间轴、面板和脚部标签。关掉后不画任何界面，只剩 `/dp` 的文字版。 |
| `mode` | `apply` | `apply` 判断并照做；`shadow` 只判断和记录，不改档位、不改模型、不加说明，也不收起 skill 列表。shadow 里 skill 列表照样记下候选，发消息时照样问 skill 的题、记一条 skill 决定，只是不加推荐；看板上写「只记录，不改」。 |
| `backend` | `drex` | `drex` 或 `jev`。 |
| `fallback` | 关 | 默认后端失败或超时时，同一次判断改问另一个后端一次。要配置两个密钥。开着时第一个后端只用时限的 60%，剩下的留给改问，总时限不变。Jev 没有校准，所以默认关。 |
| `drexApiKey`、`jevApiKey` | 空 | 两家的密钥，存为敏感值。 |
| `drexModel` | `drex-max-v1.1` | 固定版本。回答里的模型和它不一致时按失败处理。 |
| `jevModel` | `jev-latest` | Jev 用别名，只记下回答里的实际版本。 |
| `submitShift` | 开 | 发消息时定 effort。 |
| `midrunShift` | 开 | 一轮中途换 effort。 |
| `agentShift` | 开 | 派出 agent 时定模型和 effort。 |
| `skills` | 开 | 收起 skill 列表、推荐 skill（第一条消息早于列表时，到列表来时再判断）、`find-skill`。 |
| `midrunEverySteps` | 8 | 普通会话里每多少个工作步检查一次，0 为关闭，0 到 60。 |
| `midrunEveryScripts` | 1 | Code Mode 会话里每多少份脚本结果检查一次，0 为关闭，0 到 60。 |
| `midrunMaxNotes` | 4 | 一轮最多加几条说明，0 到 12。 |
| `agentModels` | `haiku,sonnet,opus` | agent 可选的模型层级，逗号分隔，从 `haiku`、`sonnet`、`opus`、`fable` 里选。 |
| `fableAgents` | 关 | 允许沿用主 agent 模型的 agent 跑在 `fable` 上（只对已知沿用主 agent 模型的类型起作用，见上面「派出 agent 时」）。 |
| `verifyEffort` | 开 | 读每次模型请求实际带的档位，和 mod 要的档位对照。只记录和显示，不一致也不重试。 |
| `progressNote` | 关 | 每个中途检查点之后另调一次模型写一份进展记录，下一次中途判断时交给决策模型。校准时看不出它有好处，用不用还没有定（见「校准」）。 |
| `progressNoteModel` | `haiku` | 写进展记录的模型。 |
| `submitTimeoutMs` | 4000 | 发消息时判断的时限（毫秒），500 到 9000。到时放行，不重试。 |
| `midrunTimeoutMs` | 2000 | 中途判断的时限（毫秒），500 到 9000。 |
| `agentTimeoutMs` | 3000 | 派出 agent 时判断的时限（毫秒），500 到 9000。 |

时限比 Nace 建议的 60 秒客户端超时短得多，这是有意的：判断的时候你或主 agent 在等。

## Code Mode 会话里

mod 不在工具调用本身上挂 hook（`tool.call` 这类事件），所以脚本内部的每次调用都不会引出决策请求，mod 也不为它们做任何决定。这些调用的结果行照样经过 mod 的 `session.append` hook，mod 在那里只记下工具名和是否失败；这会不会让脚本变慢还没有测过。中途判断的依据从对话的行里读：每份脚本结果、脚本里调用过的工具名和报错标记。mod 看到第一条只写着 `(dispatched #N)` 的 `REPL` 结果行时，就把这个会话当作 Code Mode 会话。

- 每到达一份脚本结果判断一次（`midrunEveryScripts` 为 1 时）。`REPL` 那条只写着 `(dispatched #N)` 的结果行不算一份结果。
- 结果多半在 `Poll` 的结果行里到达。要换档时，说明就加在这一行，下一次请求就是新档。
- 模型那一步没有调 `Poll` 时，结果作为一条附件到达，这种行带不了换档。mod 照常判断，把说明留到之后第一条 `REPL` 或 `Poll` 的结果行，所以新档晚一次请求生效。
- 说明行是一行英文事实，在终端里显示成以 `❯` 开头的一行，例如：

  ```
  [dispatch-pilot] effort is now high: the same failure came back after a fix.
  ```

  它不带命令语气。每加一行，上下文多几十个 token；不换档时什么也不加。
- 说明条数用完之后，脚本结果不再触发判断：换档要靠说明行才发得出去，问了也用不上。作为一条新消息进来的输入照常判断，那一步本来就带输入，换档不用说明，也不占条数。作为附件送进来的输入（后台任务的通知、agent 交回的报告）和脚本结果一样要靠说明行，也占条数。

## 发出去的内容

mod 只向两个地址发判断请求：Drex 是 `https://console.nace.ai/v1/systemone`，Jev 是 `https://api.typesafe.ai/v1/systemone`。请求体是 `model`、`state` 和 `questions`，密钥放在 `authorization` 头里。`state` 的内容只截断、不脱敏，整份不超过约 4000 token（按 UTF-8 字节数除以 3 估算）。工具结果里有什么（文件内容、命令输出，包括其中可能有的密钥），截下来的那一段就照样发出去。

每种判断的 `state` 字段（括号里是截断的上限，单位是估算的 token）：

| 判断 | `state` 的字段 |
|---|---|
| 发消息时 | `note`（一句怎么读这份内容的说明）；`request`：你这条消息（1200）；有上一轮时 `previous_turn`：上一轮你的消息（300）、助手最后的回答（300）、怎么结束的（答完、报错、被打断）、用的档位 |
| 一轮中途 | `note`；`request`：这一轮你的消息（600）；`current_level`、`steps_so_far`、`failed_steps`；`recent`：最近至多 5 步，每步是做了什么（脚本自带的说明或工具名，60）、调用过的工具名、成败、结果文字的头尾（150）；`latest`：最新这一步，结果给到 600（检查点是新输入时，`latest` 是那段输入本身，例如后台任务的通知或 agent 交回的报告）；`progressNote` 开着并且已有记录时 `progress`（已完成、还剩、原因是否查明，各 150） |
| 派出 agent | `note`；`task`：派出时的任务原文（2500）；`agent_type`；`description`（100） |
| `find-skill` | `note`；`request`：主 agent 写的那几个词（1200） |

skill 的题在 `questions` 里：发消息时第一次请求把每个候选 skill 的名字和 skill 列表里的说明作为选项发出，需要第二次请求时再发排在前面的至多三个；`find-skill` 也一样。发消息时 effort 题和 skill 题在同一次请求里。

另外两处：

- **读实际档位**（`verifyEffort`，默认开）。mod 挂 `http.fetch`，引擎每次发模型请求都经过它。mod 在进程内解析请求体，只取出顶层 `output_config.effort` 这一个词（并看 `thread` 字段和模型名，以认出主循环的请求），然后把请求原样放行。请求不改、不拦、不重发，请求体的其他内容不记录、不存储，也不发往任何地方。凭据头对 hook 本来就显示为 `[redacted]`。
- **进展记录**（`progressNote`，默认关）。开着时，每个中途检查点之后 mod 在后台调一次 `$.model.complete`，走会话自己的模型提供方和凭据，记在你的用量里。发过去的是这一轮你的消息（400）、上一份记录和最新这一步（做了什么、工具名、成败、结果的头尾，400）。写回的记录会随下一次中途判断发给决策模型。

决策记录存在本机的 `$.store`（`~/.claude/plugins/store/`）里，只留最近 200 条：每条有时间、哪一项判断、决策模型的原始回答、门槛、结果、回答里的模型版本、耗时、失败原因和 `request_id`、之后实际发出的档位，以及推荐的 skill 名或 agent 类型。不存你的消息和工具结果。

mod 从不打开 OpenTelemetry，除上面两家的接口外不向任何地方发送会话内容。

## 看板

看板有两块，画的是同一份数据：prompt 上方常驻的时间轴，和 `/dp` 打开的面板。看板只读状态，不参与任何判断。上面的档位是这一步的主循环请求实际带的档位；这一步的请求还没读到（读数关着、认不准，或者还没来）时显示这一步写的档位并标「未核对」，不拿更早一步的读数；两者不同时都写出来（「要 xhigh，实际发出 high」）。

换挡和 agent 的读数分三种，各有各的字：读到了而且一样是「已发出」，读到了但不一样是「没发出」，没读到（认不准、读数关着，或者还没来）是「未核对」。换挡的说明还排着、没放上行时写「（还没发出）」，这时没有请求能带上新档。`verifyEffort` 关着时什么也读不到，换挡都是「未核对」，不显示警告色。

### 时间轴

一轮进行中有五行（面板开着时只画前三行，下面两行的内容在面板里；第一步发出之前还没有格子，不画第 2、3 行）：

1. **现在。** 五格 `▮▮▮▯▯` 加档名；状态：`✓ 已发出`、`! 要 X，实际发出 Y`、`– 未核对`、`■ 已锁定`，第一步发出之前是 `– 这一轮刚开始`，档位是上次见到的；第几轮第几步（第一步之前写「刚开始」）；最后是会话种类，「Code Mode 会话」或「普通会话」（mod 见到第一条 `(dispatched #N)` 回执之后才算 Code Mode 会话），这一行放不下时最先省去它。
2. **步。** 这一轮每个工作步一格 `█`，颜色是那一步第一次请求实际带的档位，正在进行的那一步也有一格。后面的虚线和 `◇` 是下一次评估，再写「下次评估：…」。步数多于放得下的格数时，一格代表几步，并写明「每格 N 步」。
3. **评。** 每次评估在它那一步的格子下面标一个记号：`·` 不变，`▲` 升，`▼` 降，`×` 失败（第一格下面是发消息时那次）。一格里有几次评估时取最要紧的。后面写最近一次换挡从哪档到哪档、它的读数和原因。没有评估也没有换挡的一轮（例如锁定时）不画这一行。
4. **上次评估。** 结论、各道是非题的值、什么时候、谁答的、耗时。
5. **功能。** 按「生效」「未生效」「锁定」「关」分组列出六项功能；后端有问题时在末尾写明。

「下次评估」按触发条件写，不是倒计时：Code Mode 里写「下一份脚本结果到达时」（`midrunEveryScripts` 大于 1 时写「再 N 份脚本结果」）；普通会话里写「再 N 步」，同一失败复现或连续两步失败会提前；说明条数用完时写「本轮不再换挡」；锁定时写「不评估」；两轮之间写「发出下一条消息时」。

两轮之间时间轴折成一行：会话设定的档位、上一轮结束在哪一档、下次评估、会话种类。

决策模型想换档但没有换成时（`shadow` 模式，或者换档被拒），这不算一次换挡：记号是 `·`，上次评估写「想升到 X，未执行」或「想降到 X，未执行」。

### 面板

`/dp` 打开或关上。终端全屏并且约 110 列以上时停靠在右边，否则落到 prompt 上方。分区和顺序固定：

1. **现在**：档位、状态、第几轮第几步和会话种类（「第 7 轮 · 第 10 步 · Code Mode 会话」；两轮之间会话种类单独一行）、最近一次换挡和原因。
2. **换挡记录**：这一轮每次换挡在哪一步、从哪到哪、原因。
3. **上次评估**：结论；五档的概率条，`◂ 现在` 标出当前档；每道是非题的值和读法（是、否、拿不准）；规则算到了哪一步（例如「再升一档要上方合计 ≥ 0.70，现在 0.42」）；谁答的、耗时。失败时写原因。
4. **下次评估**：触发条件，以及这一轮还能换几次挡。
5. **功能**：每项一行，`●` 生效、`●` 未生效（加原因）、`●` 已锁定、`○` 关；最后一行是后端，后端是 Jev 时模型名后面写「（未校准）」，例如「Jev jev-latest（未校准）· 可用」。「生效」是说开关开着，而且它依赖的条件成立：有可用的后端；skill 推荐要已经拿到 skill 列表；档位核对要读到了请求。
6. **agent**：这一轮派出的每个 agent 的模型和 effort。mod 给它定了模型或 effort 的，在它第一步之后读一次 `$.agent.list()` 的 `lastRequest`，模型按层级、effort 按档名对照：`✓`（已发出）、`!`（没发出）、`–`（未核对）。mod 没动的 agent 没有记号。没有 agent 时不显示。
7. **这条消息推荐的 skill**：没有推荐时不显示。`shadow` 里记下但没推荐的 skill 后面写「（只记录，不改）」，功能里 skill 推荐那一行也写「只记录，不改」。

面板不管怎么关上（`/dp`、关闭键），时间轴都马上回到完整的几行。

### 脚部标签和 Desktop

终端脚部最右边有一个标签，例如 `dp high ✓`。

Claude Desktop 上，时间轴在输入框上方（空闲时引擎不显示它），面板是侧边的一栏，轨道、五格和概率条各画成一张图；状态行写当前档位和最近一次换挡，例如「high · ↑ 第 6 步后由 medium 升到 high」。Claude Desktop 现在自带的 Claude Code 是 2.1.325，低于这个 mod 要求的 2.1.327，所以 Desktop 上的样子在 Claude Desktop 带上 2.1.327 或更新的 Claude Code 之前只由测试验证过，还没有人亲眼看过。VS Code 和手机端不画看板。

### `/dp`

- `/dp`：打开或关上面板。面板放不出来时（`board` 关着、终端不够宽、这个端不放面板），在对话里输出文字版：后端、mod 要的档位和实际发出的档位、锁定状态、本会话最近 5 条决策。
- `/dp lock <档位>`、`/dp unlock`：本会话锁定或解锁档位，档位是 `low`、`medium`、`high`、`xhigh`、`max`。
- `/dp log [n]`：本机最近 n 条决策记录（默认 10 条，最多 200 条），含决策模型的原始回答。

## 校准

2026-11-19 在 Claude Code 2.1.328 上用 Drex `drex-max-v1.1` 校准过一次。用例 60 例，四类（发消息定档、中途换挡、派出 agent、skill 推荐）各 15 例：一半取自本仓库自己的会话记录（清理过，不在仓库里），一半由模型补写；参考答案由一个模型（Fable 5.2，xhigh）答两遍再裁定，不是人标的。每类 10 例用来调（调整集），5 例留出，只在最后问一次。完整的记录在 [eval/CALIBRATION.md](eval/CALIBRATION.md)。

因为校准而改的：

- 消息只是让接着做（「继续」这类话），而且上一轮的档位已知时，这一轮沿用上一轮的档位，别的题（包括难度那道题）都不再挪动它。
- 一轮中途发给决策模型的内容里不再有助手自己写的下一步打算：调整集上带着它没有多对任何一例。
- 门槛只改了一个：派出 agent 时降一档的门槛从 0.70 改到 0.95。其余都是初值：升一档要高于当前档的概率合计到 0.7，升到 `xhigh` 和 `max` 要到 0.8，降一档要低于当前档的概率合计到 0.7；是非题 0.7 以上算「是」、0.3 以下算「否」，中间算拿不准、不起作用；agent 换模型要到 0.8；skill 推荐用 TypeSafe cookbook 的 0.30、0.50、0.30。这组数只给 Drex `drex-max-v1.1`，别的 Drex 版本和 Jev 都用初值。

问法、档位说明的措辞、发消息时带上一轮、中途看最近 5 步、skill 的门槛，都试过别的做法，没有更好，保持原样。

每类答对的例数：

| | 发消息定档 | 中途换挡 | 派出 agent | skill 推荐 |
|---|---|---|---|---|
| 调整集（每类 10 例） | 9 | 10 | 7 | 9 |
| 留出集（每类 5 例） | 3 | 3 | 2 | 4 |

取舍都是在调整集上做的，所以调整集的分数不是公平的测试，只有留出集的分数算数。留出集一例就是 20 个百分点，只看得出明显的差别。留出集没有证实那个门槛的改动：派出 agent 的留出 5 例在初值 0.70 下对 4 例，在 0.95 下只对 2 例（两例该降到 `low` 的停在了 `medium`）。

在真实任务上的验收：8 个任务，中途换挡开着、关着各跑一次（共 16 次），两边都 8 次全部通过；开着的 8 次里有 6 次中途降了一档，没有一次升档，token 的中位数低约 5%。按事先定下的规则，这看不出中途换挡有用。

还没有定的三件事（上面写的是现在的代码）：

- 派出 agent 时降一档的门槛留在 0.95，还是改回 0.70。
- 进展记录（`progressNote`）用不用、默认开不开。调整集上不带记录和两种带记录的给法都全对，看不出它有好处；现在默认关。
- 中途换挡（`midrunShift`）留不留。验收看不出效果；现在默认开。

Jev 没有参加校准，它用 TypeSafe 文档给的起步值 0.7 和 0.3，所以凡是 Jev 的地方都标「未校准」：看板的后端行（「Jev jev-latest（未校准）· 可用」）和上次评估的「谁答的」（「Jev（未校准） · 312 ms」），`/dp` 文字版的后端行，以及 `/dp` 和 `/dp log` 里 Jev 答的每条决策。Drex 答的决策不标，包括选了 Jev、Drex 作为改问的后端答的那些。

60 例只看得出明显的差别，你的工作也未必像这些用例。所以建议先用 `mode: shadow` 在你自己的真实会话里跑一段时间，用 `/dp log` 看它会怎么判断（记录里有决策模型的原始回答），觉得合适再改回 `apply`。

```markdown
# 代码评审清单

评审的目的是让代码在合进去以后不出问题、别人看得懂。不是为了证明谁更聪明，也不是为了让代码变成你自己会写的样子。

## 一定要看的

按重要程度排：

1. **它做的是不是 PR 描述里说的那件事**。先读描述，再读代码。描述和代码对不上的时候，先问清楚，不要猜。
2. **会不会出错**：边界条件（空列表、零、负数、很长的字符串、并发的两个请求）、错误有没有被吞掉、失败以后状态是不是一致的。
3. **有没有测试能证明它是对的**。改了逻辑却没有测试，要求补；测试只测了正常路径，问一句异常路径怎么办。
4. **会不会影响别的地方**：改了一个公共函数，调用方有没有跟着看；改了接口的返回，前端和 SDK 有没有跟着改；改了数据库结构，迁移能不能在生产上安全地执行。
5. **别人以后能不能看懂**：名字是否说清楚了它是什么；复杂的地方有没有一句注释说明“为什么这么做”（不是“做了什么”）。

## 不用纠结的

- 格式：交给 `gofmt`、`prettier` 和 lint，评审里不讨论格式。
- 个人偏好：`for` 循环还是 `map`、提前返回还是 `if else`，只要清楚就行。你觉得另一种写法更好，可以提，但标成“可选”，作者不改也可以合。
- 和这个 PR 无关的旧代码：看到了旧代码的问题，另开 issue，不要要求作者在这个 PR 里一起改。

## 怎么写评论

- **说清楚是“必须改”还是“建议”**。我们约定前缀：`必须：`、`建议：`、`问题：`（只是想问清楚）、`赞：`（看到写得好的地方也说出来）。
- **对代码，不对人**。写“这里如果列表为空会 panic”，不写“你没考虑空列表”。
- **给理由**。“这里改成 X”不如“这里改成 X，因为 Y 的时候会出现 Z”。
- **能给例子就给例子**：一段改后的代码，或者一个会失败的输入。
- **一次说完**。尽量一轮评审把意见提全，不要作者改完一处你又发现新的一处，来回五六轮。

## 作者这边

- PR 尽量小。超过 400 行的改动，先想想能不能拆。
- 描述写清楚：改了什么、为什么、怎么验证的。有界面变化的，贴截图。
- 对“必须改”的意见，改完回复一句“已改”；不同意的，说出理由，讨论两轮还没结论，找第三个人。
- 不要在评审过程中往 PR 里加新的功能。

## 时间

- 收到评审请求，一个工作日内给第一轮意见。确实没空，说一声，让作者找别人。
- 小于 50 行的 PR，当天看完。
```

%% B2 解释“部分付款”状态是怎么来的（只是解释）
@@ user
客户成功那边问：为什么有的发票状态显示“部分付款”，客户说他明明付了全款。你看看“部分付款”是怎么判断的。

@@ assistant tools=Read*4,Grep*3,Bash*2
“部分付款”的判断本身没问题，客户说的情况多半是付了全款、但是分成了两笔，其中一笔还没到账或者没有关联到这张发票上。具体如下。

**状态是怎么算的**：`api/internal/invoice/status.go`

发票的状态由它关联的收款记录算出来：
- 所有关联的收款（状态是成功的）加起来等于或超过发票金额：已付款；
- 加起来大于 0 但小于发票金额：部分付款；
- 没有成功的收款：已发布（或者已逾期，如果过了到期日）。

每次有收款成功、退款成功，或者手动关联、取消关联收款时，都会重新算一次。

**客户说“付了全款”却显示部分付款，常见的几种情况**：

1. **银行转账分了两笔**：客户通过银行转账付款，分两次转（比如单笔限额），第二笔还没到账。等第二笔到了，状态会自动变成已付款。
2. **第二笔没有关联上**：银行转账的收款是按转账附言里的发票号自动关联的。如果第二笔的附言没写发票号，或者写错了，这笔钱会进“未关联的收款”，不会算到这张发票上。商户在后台「收款 → 未关联」里手动关联一下就好了。我查了一下，现在所有商户的“未关联的收款”一共有 1,412 笔，其中不少应该就是这种情况。
3. **手续费被扣了**：客户用某些跨境渠道付款时，渠道会从到账金额里扣掉手续费，到账的钱比发票金额少一点点，于是变成“部分付款”。商户可以在发票上“标记为已付款”，差额记为手续费。
4. **币种换算**：客户用另一种币种付款，按到账当天的汇率换算以后比发票金额少。目前只有极少数商户开了多币种收款，这种情况不多。

**建议客户成功那边这样回复**：先请商户在「收款 → 未关联」里看看有没有对应的那笔钱；有的话手动关联；没有的话请他们问问客户是不是分两笔付的、第二笔是否已经转出。

另外，“未关联的收款”有 1412 笔这么多，说明附言自动关联的命中率不太高。如果要改进，可以在关联时除了发票号，再用“金额相同、付款人名称相同”做一次模糊匹配，给商户推荐可能的发票。这个是改进建议，不急。

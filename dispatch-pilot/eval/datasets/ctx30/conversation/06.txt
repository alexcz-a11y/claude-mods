@@ user
有个商户写了个脚本，一秒钟打我们几百次 `GET /v1/invoices`，昨天下午把 API 拖慢了，webhook 投递也跟着积压。要做限流。你先说说要考虑什么，先别写代码。

@@ assistant tools=Read*5,Grep*4 mark=E12
先说现状，再说要考虑的点。

**现状**
- API 没有任何限流。`api/internal/middleware/` 下只有鉴权、日志、恢复、CORS 四个中间件。
- api 有 6 个副本，前面是 ingress-nginx，ingress 上也没有配 `limit-rps`。
- webhook 投递在 worker 里（`worker/webhook/dispatch.go`）：16 个并发 goroutine 从 `jobs` 表取任务，对每个商户的回调地址发 POST，失败按指数退避重试。昨天积压是因为那个商户的脚本同时触发了大量 `invoice.updated` 事件，一个商户的任务把 16 个并发占满了，别的商户的回调排在后面。
- worker 的任务队列（`worker/queue`）是按 `scheduled_at` 先进先出，不区分商户。
- Redis 已经有了（缓存用），单主一从，没有开集群。

**要考虑的点**

1. **在哪一层限**：
   - ingress 层按 IP 限最简单，但商户的脚本可能跑在多台机器上，而且很多商户在同一个 NAT 后面，按 IP 会误伤；
   - 应用层按 API key（也就是按商户）限更准确，要放在鉴权中间件之后。
2. **计数放在哪**：6 个副本各自计数的话，一个商户实际能拿到 6 倍的额度，而且请求在副本间的分布不均匀。要准确就得放 Redis，用 Lua 脚本做令牌桶，每个请求多一次 Redis 往返（同机房 0.3 毫秒左右）。
3. **Redis 挂了怎么办**：放行（fail-open）还是拒绝（fail-closed）。放行的话限流在 Redis 出问题时等于没有；拒绝的话 Redis 一抖所有商户的 API 都不可用。也可以退化成每个副本本地计数，额度除以 6。
4. **额度怎么定**：按套餐给不同额度，还是统一一个数；读接口和写接口分开算；突发量（桶的容量）给多少。需要先拿访问日志统计一下现在各商户的峰值，不然会误伤正常用户。
5. **超限的返回**：`429 Too Many Requests` 加 `Retry-After`，以及 `X-RateLimit-Remaining` 之类的头。我们的 SDK（`sdk/js`、`sdk/python`）现在遇到 429 不会重试，要一起改，不然商户那边会直接报错。
6. **webhook 投递要不要单独限**：API 限住了，事件还是可能大量产生（比如批量改发票）。投递这边需要按商户限并发，比如每个商户最多同时 2 个投递，否则一个商户还是能占满 16 个并发。
7. **队列公平性**：worker 的任务队列先进先出，一个商户一次塞进 5 万个任务，别的商户的任务就要排在后面。要改成按商户轮转取任务，或者每个商户一个虚拟队列。这会动 `worker/queue` 的取任务 SQL，那段代码还和 lease 的逻辑绑在一起。
8. **白名单和临时调额**：大客户临时要导数据，要能在后台给某个商户临时提高额度，这需要一张配置表和后台页面。
9. **观测**：每个商户的 429 次数要能在 Grafana 上看到，超限时要有日志，不然客服没法回答“为什么我的请求被拒了”。

这几块落在 api 的中间件、worker 的 webhook 投递和任务队列三个地方，还有 Redis 和 SDK，彼此有关联：比如 Redis 的故障策略同时影响 API 和投递。

产品发了一份下个季度的需求，商户子账号和角色权限。我贴一下，你先看看技术上有什么要注意的，不用写方案，列问题就行：

> **商户子账号与角色（草案 v0.3）**
>
> **背景**：现在一个商户只有一个登录账号，老板、会计、销售共用一个账号密码，出了问题查不到是谁做的，离职员工也没法收回权限。超过 40% 的付费商户在客服渠道提过这个需求，是续费调研里排第一的诉求。
>
> **目标**：
> 1. 一个商户可以邀请多个成员，每个成员用自己的邮箱登录；
> 2. 每个成员有一个角色，角色决定能做什么；
> 3. 关键操作有操作日志，能看到是谁在什么时候做了什么；
> 4. 老板（所有者）可以随时移除成员，移除后立即失去访问权限。
>
> **角色（第一期固定四个，不支持自定义）**：
> - 所有者：全部权限，包括管理成员、修改收款账户、注销商户。每个商户有且只有一个所有者，可以转让。
> - 管理员：除了“修改收款账户”“注销商户”“转让所有者”之外的全部权限。
> - 会计：查看全部发票和收款，开票、作废、退款、导出；不能管理成员、不能改商户设置。
> - 销售：只能看到和操作自己创建的客户和发票；不能退款、不能导出、不能看收款汇总。
>
> **操作日志**：记录登录、成员变更、开票、作废、退款、导出、修改设置、修改收款账户。保存 1 年，所有者和管理员可以在后台查看和筛选。
>
> **其他**：
> - 成员邀请通过邮件，链接 72 小时有效；
> - 现有的账号自动成为所有者；
> - API key 也要归属到成员，成员被移除时他创建的 API key 同时失效；
> - 第二期再做：自定义角色、按门店划分数据权限、单点登录。
>
> **期望上线**：明年 1 月。

**一、身份模型要改的地方**

1. **现在“用户”和“商户”是一对一的**：`users` 表里有 `merchant_id`，一个用户只能属于一个商户。草案只要求“一个商户多个成员”，但实际上会计事务所的会计会同时服务好几个商户，他们会希望一个邮箱加入多个商户。如果第一期不支持，以后再改会很痛。建议和产品确认：一个邮箱能不能属于多个商户？如果能，就要加一张 `memberships(user_id, merchant_id, role)`，登录后要选择进入哪个商户，所有接口里“当前商户”的来源都要改。
2. **会话里存的是什么**：现在登录后的会话（`sess:` 前缀的 Redis key）里存了 `user_id` 和 `merchant_id`，每个接口直接从会话里拿 `merchant_id` 做数据隔离。如果一个用户可以属于多个商户，会话里就要存“当前选中的商户”，切换商户时更新。
3. **现有账号变成所有者**：迁移时给每个商户现有的那个用户建一条所有者的成员关系。这一步本身不复杂，但要注意有 300 多个商户是“同一个邮箱注册了两次”（以前允许的），合并还是保持分开，需要产品给个说法。

**二、权限检查放在哪里**

4. **现在没有权限检查，只有商户隔离**：所有接口都只检查“这条数据是不是当前商户的”，没有“这个人能不能做这件事”的概念。加角色以后，要给大约 140 个接口（`api/openapi.yaml` 里的操作数）逐个标上需要的权限。建议用一个声明式的中间件：在路由注册的地方写上需要的权限，中间件统一检查，而不是在每个 handler 里写 if。漏标的接口要能被测试发现（比如一个测试遍历所有路由，没有标权限的直接失败）。
5. **“销售只能看自己创建的”是数据级的权限**：这不是在路由上加个检查就能解决的，所有列表查询（发票、客户、导出）都要按角色加一个“创建人是自己”的条件，统计类的接口（首页汇总、报表）也要跟着变。这是工作量最大的一块，建议估算时单独列出来。另外，现在 `invoices` 和 `customers` 上没有记录“创建人”，要加 `created_by` 列，历史数据的创建人是空的，销售角色看不到历史数据，需要产品确认这样是否可以接受。
6. **API key**：现在 API key 属于商户。草案要求归属到成员、成员移除时失效。那 API key 的权限是不是也跟着成员的角色？如果一个销售创建了 API key，用这个 key 能不能退款？建议明确“API key 继承创建者的角色”，否则会出现绕过角色的口子。

**三、操作日志**

7. **写日志的位置**：要记录的 8 类操作分散在 api 的十几个 handler 和 worker 的几个任务里（比如导出是在 worker 里完成的）。建议做成一个统一的 `audit.Record(ctx, action, target, detail)`，在业务事务里一起写，保证“操作成功了日志一定在”。
8. **量**：按现在的操作量估算，所有商户加起来每天大约 300 万条操作，保存 1 年是 10 亿条级别。放在主库的一张普通表里会影响主库，建议按月分区，或者直接写到单独的存储（比如 ClickHouse），后台查询走那边。
9. **“谁做的”在后台任务里怎么记**：比如定时发送的逾期提醒、自动重试的 webhook，它们不是某个成员触发的，日志里的操作人要有一个“系统”的取值。

**四、和现有功能的交叉**

10. **邀请邮件**：72 小时有效的邀请链接，接受以后失效；同一个邮箱被重复邀请时，以最后一次为准，之前的链接作废；被邀请的邮箱已经是别的商户的成员时怎么处理，取决于第 1 条的答案。
11. **移除成员要“立即”失去权限**：会话在 Redis 里，移除成员时要把他的所有会话删掉；API key 要立即失效（现在 API key 的校验结果在进程内缓存了 60 秒，要改成移除时主动失效，或者把缓存时间缩短）。
12. **前端**：后台所有页面都要根据角色隐藏没有权限的按钮和菜单，这是体验问题，不是安全问题（真正的检查在后端），但工作量不小，阿杰那边要单独估。

**五、需要产品确认的问题**（汇总）

- 一个邮箱能否属于多个商户？
- 同一个邮箱重复注册的 300 多个商户怎么处理？
- 销售角色看不到没有创建人的历史数据，是否可以接受？
- API key 是否继承创建者的角色？
- 操作日志的查询需要支持哪些筛选条件？导出要不要？

总的来说，第 1、4、5 条是骨架性的改动，决定了后面所有接口怎么写，最好在开工前定下来；操作日志相对独立，可以并行做。

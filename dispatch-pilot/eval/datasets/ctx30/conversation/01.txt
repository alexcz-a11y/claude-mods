**1. 调度：`worker/cmd/payout-worker/main.go`**

`payout-worker` 是单独的 Deployment，和跑提醒、导出、通知的普通 `worker` 分开部署。进程里只有一个定时任务：

```go
c := cron.New(cron.WithLocation(time.UTC))
c.AddFunc("5 * * * *", func() { payout.RunBatch(ctx, deps) })
```

每个整点过 5 分跑一次。注释里写了原因：银行那边整点有一个对账窗口，整点前后几分钟接口偶尔返回 `503 settlement in progress`。同一时刻只允许一个实例跑批：`RunBatch` 一开始先 `SELECT pg_try_advisory_lock(42001)`，拿不到锁就直接 return，日志打 `batch skipped: lock held`。Helm 里 `payout-worker` 的副本数是 2，所以平时总有一个实例在空转等锁。

**2. 选单：`worker/payout/batch.go` 的 `RunBatch`**

```go
rows, err := q.ListDuePayouts(ctx, store.ListDuePayoutsParams{
    Status:      "pending",
    ScheduledAt: now,
    Limit:       5000,
})
```

对应的 SQL 在 `api/queries/payouts.sql`：

```sql
-- name: ListDuePayouts :many
SELECT id, merchant_id, bank_account_id, amount, currency, scheduled_at
FROM payouts
WHERE status = $1 AND scheduled_at <= $2
ORDER BY scheduled_at, id
LIMIT $3
FOR UPDATE SKIP LOCKED;
```

**3. 金额换算：`worker/payout/amount.go`**

`payouts.amount` 是 `numeric(12,2)`，sqlc 映射成 `pgtype.Numeric`，代码里先转成 `decimal.Decimal`（shopspring 的库）做加总，调银行接口之前再转成“分”：

```go
func toMinor(d decimal.Decimal) (int64, error) {
    m := d.Mul(decimal.NewFromInt(100))
    if !m.Equal(m.Truncate(0)) {
        return 0, fmt.Errorf("amount %s has more than 2 decimals", d)
    }
    return m.IntPart(), nil
}
```

`toMinor` 出错时整组 payout 都会被跳过，状态留在 `pending`，下一个小时再试，日志里是 `skip group: amount ... has more than 2 decimals`。我在日志查询里没法看生产，只能从代码看到这个分支存在。

**4. 调银行：`worker/payout/bank/client.go`**

`Transfer(ctx, TransferRequest)` 用 HTTPS POST 调银行的代付接口。请求体里带一个 `idempotency_key`，银行的接口文档（`docs/vendor/bank-api-v3.pdf` 第 14 页）承诺同一个 key 在 24 小时内只执行一次。这个 key 在 `batch.go` 里生成：

```go
func groupKey(ids []int64) string {
    slices.Sort(ids)
    h := sha256.New()
    for _, id := range ids {
        fmt.Fprintf(h, "%d,", id)
    }
    return hex.EncodeToString(h.Sum(nil))[:32]
}
```

也就是按这一组 payout 的 id 排序后算哈希，同一组重跑会得到同一个 key。HTTP 超时 25 秒，失败按 `retry.Exponential(2*time.Second, 3)` 重试 3 次，重试用的是同一个 key。

**5. 写回：`worker/payout/batch.go` 的 `markSent` 和 `markFailed`**

银行返回 `accepted` 时，在同一个事务里把这一组 payout 的 `status` 改成 `sent`，写 `bank_ref` 和 `sent_at`。返回 `rejected` 或者重试用尽时走 `markFailed`：`status` 改成 `failed`，`failure_reason` 存银行给的原因码（比如 `AC04 账户已销户`）。`failed` 的记录不会自动重试，要运营在后台点“重新打款”，后台会新建一条 `pending` 的 payout，旧的那条保留。

**6. 对账：`worker/payout/reconcile.go`**

每天凌晨 3 点拉银行前一天的流水文件，按 `bank_ref` 去对 `status = 'sent'` 的记录，金额也比一遍，对上了改成 `settled`；对不上的写进 `payout_mismatches` 表，第二天财务人工处理。

读代码时注意到的几点，只是记录，没有改：

- 读 `amount` 的地方一共三处：`batch.go` 的加总、`reconcile.go` 的对账比较、`api/internal/payout/handler.go` 给后台展示。三处都经过 `decimal.Decimal`，没有用 float。
- `payouts` 上有 4 个索引：主键、`(status, scheduled_at)`、`(merchant_id, created_at)`，还有 `bank_ref` 上的唯一索引。
- 迁移里最近一次动这张表是 `migrations/0027_payouts_failure_reason.sql`，加了一列可空的 `failure_reason text`。
- `groupTransfers`、`toMinor`、`markFailed` 都没有单元测试，`worker/payout/` 下只有 `bank/client_test.go` 一个测试文件。

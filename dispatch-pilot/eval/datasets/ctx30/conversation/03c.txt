**口径**（写在这里方便财务核对）：
- 订阅收入 = `subscription_invoices` 里 `status = 'paid'` 的 `amount`，按 `period_start` 所在的月份归属，不是按付款时间；
- 套餐按账单上的 `plan_code`（月中升级的商户，升级前后两张账单各算各的套餐）；
- 付费商户数 = 当月有至少一张已付账单的商户，去重；
- 退款不扣减（`subscription_refunds` 这个季度一共 23 笔、合计 6,140 元，单独列在最后）；
- 金额单位：元，含税。

**查询**：

```sql
SELECT date_trunc('month', si.period_start)::date AS month,
       si.plan_code,
       count(DISTINCT si.merchant_id)              AS paying_merchants,
       sum(si.amount)                              AS revenue
FROM subscription_invoices si
WHERE si.status = 'paid'
  AND si.period_start >= '2026-07-01' AND si.period_start < '2026-10-01'
GROUP BY 1, 2
ORDER BY 1, 2;
```

%% X2-4 api 到 worker 的请求 ID 传递（已做完）
@@ user
现在排查问题的时候，api 的日志和 worker 的日志对不上：一个请求触发了后台任务，任务的日志里没有那个请求的 request_id。加一下。

@@ assistant tools=Read*6,Grep*3,Edit*7,Bash*3
加好了，现在从 api 进来的请求触发的任务，日志里都带同一个 `request_id`。

**现状**：
- api 的 `middleware.RequestID` 给每个请求生成 `request_id`（或者沿用 `X-Request-Id` 请求头），放进 `context`，`zerolog` 的每条日志自动带上；
- 入队的地方（`worker/queue.Enqueue(ctx, job)`）只把 `type` 和 `payload` 写进 `jobs` 表，ctx 里的东西丢了；
- worker 取到任务后，日志里只有 `job` 和 `type`。

**改动**：
1. 迁移 `migrations/202610141020_jobs_meta.sql`：`jobs` 加一列 `meta jsonb NOT NULL DEFAULT '{}'`。`jobs` 表是队列表，生产上常态只有几千行，`ADD COLUMN ... DEFAULT` 在 PG 15 上只改元数据，不重写表。
2. `worker/queue/enqueue.go`：入队时从 ctx 里取 `request_id` 和 `merchant_id`，写进 `meta`。
3. `worker/queue/consume.go`：取到任务后把 `meta` 里的值放回 ctx，再交给任务的处理函数，这样处理函数里的日志自动带上。
4. 任务里再入队的子任务（比如发票发送任务再入队一个 webhook 投递任务），`meta` 会顺着 ctx 传下去，同一个 `request_id` 能串起整条链路。
5. 测试：`queue` 包加了 2 个用例：入队时写 `meta`、消费时还原到 ctx。

**效果**（本地）：

```
api     12:01:07 INF invoice sent request_id=3f2c9a merchant_id=90001 invoice_id=771203
worker  12:01:07 INF job start request_id=3f2c9a job=104412 type=webhook.deliver
worker  12:01:08 INF webhook delivered request_id=3f2c9a job=104412 status=200
```

Loki 里按 `request_id` 搜，就能同时看到 api 和 worker 的日志。

%% X2-5 Redis 内存告警：缓存的 key 没有过期时间（已做完）
@@ user
Redis 内存告警，用到 85% 了。我们 Redis 只放缓存，怎么会涨这么多？

@@ assistant tools=Bash*5,Read*3,Grep*2,Edit*2
原因找到了，有一类 key 没有设过期时间，已经改了。

**看了什么**：用 `redis-cli --bigkeys` 和按前缀抽样统计（在只读副本上跑的 `SCAN`，没有用 `KEYS`）：

| 前缀 | key 数 | 内存占比 | 有过期时间 |
|---|---|---|---|
| `ms:`（商户设置缓存） | 61,204 | 7% | 是（10 分钟） |
| `inv:pdfmeta:`（发票 PDF 的元信息） | 2,904,118 | 81% | **否** |
| `sess:`（后台会话） | 48,991 | 9% | 是 |
| 其他 | — | 3% | — |

`inv:pdfmeta:` 是 `api/internal/invoice/pdfmeta.go` 写的：每张发票生成 PDF 时，把页数、文件大小、生成时间缓存起来，给发票详情页显示。写的时候用的是 `SET key value`，没有 `EX`。发票只增不减，这个前缀就一直涨。

**改法**：
1. `pdfmeta.go` 写入时加 30 天过期：`rdb.Set(ctx, key, value, 30*24*time.Hour)`。读不到时本来就会重新算（读 PDF 文件头），所以过期不影响功能。
2. 存量的 290 万个 key 没有过期时间，写了一个一次性的脚本 `scripts/redis-expire-pdfmeta.sh`：用 `SCAN` 按前缀遍历，对每个 key `EXPIRE` 一个 1 到 30 天之间的随机时长（避免同一时刻集中过期），每批 1000 个，批之间停 50 毫秒。在 staging 上跑过，2 万个 key 用了 4 秒。

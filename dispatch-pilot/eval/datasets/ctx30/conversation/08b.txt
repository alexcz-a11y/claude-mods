@@ assistant tools=Read*6,Grep*3,Edit*8,Bash*4
加好了，在 Tempo 里能看到完整的一条 trace，从 api 的请求一直到 worker 的 webhook 投递。

**接入**：
1. `go.opentelemetry.io/otel` 和 OTLP 的 gRPC exporter，初始化放在新的 `internal/telemetry/telemetry.go`，api 和 worker 的 `main.go` 各调一次 `telemetry.Init(ctx, serviceName)`；

3. 采样：生产 10%（`ParentBased(TraceIDRatioBased(0.1))`），staging 100%。

**span**：
- api：`otelhttp` 中间件包住整个 router，每个请求一个根 span，名字用路由模板（`POST /v1/invoices/{id}/send`），不用实际路径，避免基数爆炸；
- 发送流程里手动加了三个子 span：`invoice.render_pdf`、`invoice.send_email`、`queue.enqueue`；
- pgx 用 `otelpgx` 加了 tracer，每条查询一个 span，SQL 只记录语句模板，不记录参数；
- worker：取任务时从 `jobs.meta`（前面加的那列）里取出 trace 上下文，作为父 span 继续，所以 webhook 投递的 span 和 api 的请求在同一条 trace 里。

%% X1-3 api 的镜像太大（已做完）
@@ user
api 的镜像 1.1G，拉一次要好久，发布时 Pod 起得慢。能不能小一点？

@@ assistant tools=Read*2,Edit*2,Bash*5
改好了，api 镜像 1.12 GB → 31 MB，worker 1.18 GB → 64 MB。

**原因**：`docker/api.Dockerfile` 是单阶段的，直接 `FROM golang:1.22.8-bookworm`，在里面编译完就运行，整个 Go 工具链、源码、模块缓存都在镜像里。

**改法**：多阶段构建：

```dockerfile
FROM golang:1.22.8-bookworm AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -trimpath -ldflags "-s -w -X main.version=${VERSION}" -o /out/api ./api/cmd/server

FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=build /out/api /api
COPY --from=build /src/assets /assets
USER nonroot:nonroot
ENTRYPOINT ["/api"]
```

几点说明：
- `CGO_ENABLED=0`：api 没有用到 cgo，静态编译后可以用 distroless 的 static 镜像；
- `assets/`（字体和模板）要一起拷进去，PDF 渲染要用；
- distroless 里没有 shell，`kubectl exec` 进不去了。排查时可以用 `kubectl debug` 挂一个临时容器，我在 `docs/ops/debugging.md` 里加了一段说明；
- worker 的镜像大一些，因为它多拷了一份中文字体的粗体。

**验证**：本地 `docker build` 两个镜像，起来跑了一遍 e2e，通过；在 staging 上部署了一次，Pod 从拉镜像到就绪由 48 秒降到 9 秒。

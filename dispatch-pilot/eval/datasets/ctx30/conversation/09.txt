先说现在的实现，再说看到的现象。

**异步导出的实现**（昨天上线的 PR #836）：
- `POST /v1/exports/pdf` 只创建一条 `exports` 记录（状态 `queued`），往 `jobs` 表插一个 `export.pdf` 任务，立刻返回 `202` 和导出 ID；
- `worker` 里的消费者取到任务，状态改成 `processing`，逐张渲染、写进临时 zip，完成后上传到 `s3://ledgerly-exports/`，状态改成 `done`，写下载地址；
- 前端每 3 秒轮询 `GET /v1/exports/{id}`；
- 渲染代码复用了 api 里的 `invoice/pdf` 包，包括上一次加的字体和模板缓存。

**看到的现象**（你给的三个导出 ID，我在 worker 的日志里按 `export_id` 搜）：

```
10:12:04 worker-5f8d export_id=7731 job=95102 start invoices=420
10:12:35 worker-0b2c export_id=7731 job=95102 start invoices=420
10:13:06 worker-9e41 export_id=7731 job=95102 start invoices=420
...（之后每隔 31 秒左右又有一次 start，一直到 10:33）
10:34:12 worker-5f8d export_id=7731 job=95102 failed: attempts exhausted (40)
```

日志里只有 `start`，没有一次 `rendered` 或者报错。每 31 秒换一个 worker 重新 start，看起来像是任务 lease 到期被别人领走了。但是第一个 worker 的那次执行去哪了：没有完成的日志，没有错误日志，也没有 panic，进程没有重启（Pod 的 restart 次数没变）。

我能想到的几种可能：
1. 渲染本身卡住了（比如某张发票的数据让 gofpdf 进入死循环），每个执行者都卡在同一张上，lease 到期后被别人领走，别人也卡住；
2. 渲染没卡，只是太慢，每 31 秒被抢一次，前面的执行者其实还在跑，但 worker 的日志级别是 info，渲染过程没有日志；
3. 内存：worker 的 limit 是 2Gi，420 张发票在内存里攒一个 zip，加上字体缓存，可能接近上限，但没有 OOM 的记录；
4. 上传 S3 卡住：如果卡在上传，应该能看到 `rendered` 日志，现在没有。

现在分不清是哪一个，可能要加日志、在 staging 上用同一个导出 ID 的数据复现才能知道。三次修改了，问题还在，我也没有把握下一步一定能找到原因。

```markdown
# 未关联收款的推荐匹配（草稿）

## 现状

银行转账到账后，系统按转账附言里的发票号自动关联发票。附言里没有发票号、发票号写错、
或者一笔钱付了多张发票时，这笔收款会进入「收款 → 未关联」，由商户手动关联。

目前所有商户的未关联收款共 1,412 笔，涉及 611 个商户，最早的一笔是 5 个月前的。
抽样看了 100 笔，原因大致是：

| 原因 | 占比 |
|---|---|
| 附言里没有发票号（只写了公司名或“货款”） | 46% |
| 发票号写错（少一位、多一位、字母大小写） | 21% |
| 一笔钱付了多张发票 | 17% |
| 金额和任何一张发票都对不上（扣了手续费、部分付款） | 11% |
| 其他（退款退回、转错账） | 5% |

## 目标

不自动关联，只推荐：在未关联收款旁边显示“可能是这几张发票”，商户点一下确认。
自动关联错了的代价是对账错乱，商户很难发现；推荐错了商户不点就行。

## 推荐的规则（按顺序，命中就停）

1. **发票号近似**：附言里有一个和某张未付发票号编辑距离为 1 的字符串（覆盖“少一位、多一位、写错一个字符”）。
2. **金额和付款人都对得上**：同一个商户下，未付发票里金额等于这笔收款、客户名称和付款人户名相似（去掉“有限公司”等后缀以后包含关系成立）。
3. **金额等于几张发票之和**：同一个客户名下，有 2 到 4 张未付发票的金额加起来等于这笔收款。超过 4 张不找，组合太多。
4. **金额接近**：同一个客户名下，有一张未付发票的金额比这笔收款多 0.1% 到 2%（可能是手续费）。这一条只推荐、标注“金额有差异”。

每笔收款最多推荐 3 个候选，按规则顺序排。

## 预计效果

用那 100 笔抽样手算：规则 1 能覆盖“写错发票号”的大部分（21 笔里 18 笔），规则 2 能覆盖“附言没写发票号”的一半左右（46 笔里约 25 笔），规则 3 能覆盖“一笔付多张”的大部分（17 笔里 13 笔），规则 4 能覆盖 6 笔。
合计约 62% 的未关联收款能得到正确的推荐。

## 要和产品确认的

1. 推荐出现在哪里：只在「未关联」列表里，还是收款到账时也给商户发通知？
2. 商户确认推荐以后，要不要记住“这个付款人户名对应这个客户”，下次直接推荐？
3. 规则 4（金额有差异）确认以后，差额怎么记：手续费、坏账，还是让商户选？

## 不做的

- 不自动关联，所有关联都要商户确认。
- 不处理跨商户的情况（一笔钱转错到别的商户）。
```

%% C2 功能开关要不要换成第三方服务（只讨论）
@@ user
产品想做灰度发布，按商户逐步打开新功能。我们现在的功能开关是写在配置里的，改一次要发布一次。要不要换成第三方的功能开关服务？你比较一下自己做和用第三方，给个建议。

@@ assistant tools=Read*4,Grep*3
先说现状，再比较，最后给建议。

**现状**

开关定义在 `api/internal/config/flags.go`，值来自环境变量，Helm 的 values 里按环境写死。全仓库现在有 14 个开关，其中 9 个是长期的配置项（比如某个渠道是否启用），只有 5 个是真正的“功能开关”（新功能上线前关着，上线后打开，过一段时间删掉）。所有开关都是全局的，不能按商户打开。改一个开关要改 values、走一次发布。

**产品要的**

按商户（或者按套餐、按比例）逐步打开新功能；出问题时能在几分钟内关掉，不用发布；能看到每个开关现在对哪些商户是开的。

**方案一：自己做**

- 一张 `feature_flags` 表（开关名、默认值、规则），规则支持：全部开、全部关、指定商户列表、按套餐、按商户 ID 取模的百分比；
- api 和 worker 启动时加载，之后每 30 秒刷新一次（或者用 PostgreSQL 的 `LISTEN/NOTIFY` 在修改时推送）；
- 后台加一个内部管理页面，只有我们的员工能访问，用来改开关，每次修改记日志；
- 估计工作量：后端 4 到 5 天，管理页面 2 到 3 天。

**方案二：用第三方服务**

- 主流的服务都支持我们要的所有规则，还有现成的管理界面、修改记录、SDK；
- SDK 会在本地缓存规则，第三方服务挂了不影响判断，只是改不了；
- 费用：按我们的规模（3 个服务、二十来个开发者），常见的服务每月大概几百到一千多美元；
- 数据：判断开关时要把商户 ID、套餐这类属性传给 SDK。大部分服务的 SDK 是在本地判断的，不会把这些属性发出去，但要逐个确认，涉及客户数据出境的话要过法务。

**比较**

| | 自己做 | 第三方 |
|---|---|---|
| 一次性工作量 | 一到两周 | 一到两天接入 |
| 每月费用 | 几乎为零 | 几百到一千多美元 |
| 规则的灵活程度 | 够用，以后要什么加什么 | 很全，很多用不上 |
| 改开关的速度 | 30 秒内生效 | 几秒内生效 |
| 依赖 | 只依赖自己的数据库 | 多一个外部服务和合同 |
| 合规 | 不涉及 | 要确认数据不出境 |

**建议**：自己做。我们只有 5 个真正的功能开关，需求就是“按商户、按套餐、按比例”这三种规则，自己做一周多就能满足，而且不用处理外部服务的合同和数据合规问题。等哪天开关多到几十个、需要做 A/B 实验和统计分析了，再考虑第三方。

另外，不管选哪个方案，建议顺便把那 9 个长期配置项从“功能开关”里分出去，它们不应该被灰度。

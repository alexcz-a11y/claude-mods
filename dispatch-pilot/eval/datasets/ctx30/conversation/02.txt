@@ assistant tools=Grep*2,Read*5,Bash*3
看了一下，导出是同步做的，整条路径如下。

**接口**：`POST /v1/exports/pdf`，handler 在 `api/internal/export/pdf.go`：

```go
func (h *Handler) ExportPDF(w http.ResponseWriter, r *http.Request) {
    ids, err := decodeIDs(r)
    if err != nil {
        httpx.Error(w, r, err)
        return
    }
    w.Header().Set("Content-Type", "application/zip")
    w.Header().Set("Content-Disposition", `attachment; filename="invoices.zip"`)
    zw := zip.NewWriter(w)
    for _, id := range ids {
        inv, err := h.store.GetInvoiceWithLines(r.Context(), id)
        if err != nil {
            log.Ctx(r.Context()).Error().Err(err).Int64("invoice_id", id).Msg("export: load")
            continue
        }
        f, _ := zw.Create(inv.Number + ".pdf")
        if err := h.renderer.Render(r.Context(), inv, f); err != nil {
            log.Ctx(r.Context()).Error().Err(err).Int64("invoice_id", id).Msg("export: render")
        }
    }
    zw.Close()
}
```

整个 zip 边渲染边写进响应，所有发票在一个请求里串行处理。

**渲染**：`api/internal/invoice/pdf/render.go`，用的是 gofpdf。每张发票都会 `gofpdf.New("P", "mm", "A4", "")`，然后 `AddUTF8Font("NotoSansSC", "", fontPath)` 加载中文字体（`assets/fonts/NotoSansSC-Regular.ttf`，5.8 MB），粗体再加载一次 `NotoSansSC-Bold.ttf`（6.1 MB），然后按模板画抬头、明细表格、合计和备注。

**超时**：两层都是 30 秒。
- ingress：`deploy/helm/api/values.yaml` 里 `nginx.ingress.kubernetes.io/proxy-read-timeout: "30"`；
- 服务端：`api/cmd/server/main.go` 里 `http.Server{ReadTimeout: 10 * time.Second, WriteTimeout: 30 * time.Second}`。

30 秒内没写完，ingress 先断开，客户端看到 504。

**本地测了一下**（`go test -run XXX -bench BenchmarkExportPDF -benchtime 1x ./api/internal/export/`，用种子数据里同一个商户的发票，每张 8 行明细）：

| 张数 | 耗时 |
|---|---|
| 50 | 9.8s |
| 100 | 20.4s |
| 200 | 41.7s |
| 400 | 88.0s |

基本线性，每张约 0.2 秒，200 张就超过 30 秒，和客户说的对得上。

**先做了一个最直接的改动**：把两层超时都调到 120 秒。
- `deploy/helm/api/values.yaml`：`proxy-read-timeout: "120"`、`proxy-send-timeout: "120"`；
- `api/cmd/server/main.go`：`WriteTimeout: 120 * time.Second`。

PR #812。说明两点，都写进了 PR 描述：
1. 这只是让 500 张以内能在 2 分钟里出来，不解决渲染慢本身。800 张按每张 0.2 秒算要 160 秒，还是会超。
2. `WriteTimeout` 是整个 server 的设置，120 秒对 api 的所有接口都生效，慢客户端能占住连接更久。目前 api 有 6 个副本、每个副本最多 512 个并发连接，影响不大，但值得知道。

要根治得把导出挪到后台任务（前端轮询或者发邮件给下载链接），或者让渲染变快，这两件事都比调超时大得多。

%% D1 发票号为什么会跳号（只是解释）
@@ user
问个事：发票号是怎么生成的？有客户问为什么他们的发票号中间跳了几个，以为我们丢了数据。

@@ assistant tools=Grep*2,Read*3
发票号的生成在 `api/internal/invoice/number.go`，逻辑不复杂，跳号是预期内的，不是丢数据。

**怎么生成的**

每个商户在 `invoice_counters` 表里有一行计数器（主键 `merchant_id`，字段 `prefix`、`next_value`、`year`）。新建发票时在同一个事务里：

```go
func (s *Service) nextNumber(ctx context.Context, tx store.Querier, merchantID int64, issuedYear int) (string, error) {
    c, err := tx.BumpInvoiceCounter(ctx, store.BumpInvoiceCounterParams{MerchantID: merchantID, Year: int32(issuedYear)})
    if err != nil {
        return "", err
    }
    return fmt.Sprintf("%s%d-%05d", c.Prefix, c.Year, c.Value), nil
}
```

`BumpInvoiceCounter` 是一条 `UPDATE invoice_counters SET next_value = CASE WHEN year = $2 THEN next_value + 1 ELSE 1 END, year = $2 WHERE merchant_id = $1 RETURNING ...`，行锁保证同一个商户并发建发票时不会拿到同一个号。因为和插入发票在同一个事务里，插入失败回滚时计数器也会回滚，所以失败的请求不会造成跳号。

**为什么会跳**

1. **草稿被删除**：默认设置下，发票在创建草稿时就分配号码（`merchant_settings.number_on_issue = false`）。草稿删掉，号码不会回收。看了一下这个客户（商户 ID 你没给，我按“跳号”查了种子数据里的类似情况）：典型的是建了草稿又删掉，号码就空出来了。
2. **作废的发票**：作废后号码保留，列表默认不显示作废的发票（筛选里勾上“已作废”才看得到），客户可能以为是跳号。
3. **跨年重置**：`year` 变了以后从 1 开始，新年第一张是 `INV2026-00001`，不算跳号，但有客户会误会。

**怎么避免**

商户设置里有“发布时才编号”（`number_on_issue = true`）：草稿没有号码，点“发布”时才分配。打开以后删草稿不会再空出号码。作废的还是会保留号码，这是税务上要求的，不能回收。

@@ user
明白了，我跟客户说开“发布时才编号”，作废的在筛选里能看到。

@@ assistant

**失败分支**：`worker/payout/batch.go` 里重试用尽或银行明确拒绝时调用

```go
func (b *Batch) markFailed(ctx context.Context, group []store.Payout, reason string) error
```

   ```go
   func SendPayoutFailed(ctx context.Context, webhookURL string, p store.Payout, reason string) error {
       text := fmt.Sprintf("Payout %d 失败：%s %s → 商户 %d，原因：%s",
           p.ID, p.Amount.String(), p.Currency, p.MerchantID, reason)
       return PostMessage(ctx, webhookURL, text)
   }
   ```

2. `worker/payout/batch.go` 的 `markFailed` 成功提交事务之后，对这组里的每一笔调 `SendPayoutFailed`。一组最多几十笔，一笔一条消息，频道里能直接搜 payout ID。

5. 测试：`PostMessage` 已经有 `slacktest` 的用例覆盖，`SendPayoutFailed` 只是拼一句话再调它，我觉得不用单独加；`batch.go` 现在本来就没有测试。

%% S14 PDF 上的日期差一天：原因是时区（E07）
@@ user
有个客户说 PDF 上的开票日期比他实际开票那天早一天，他在悉尼。我看了一下后台页面上显示的是对的，只有 PDF 不对。

@@ assistant tools=Grep*4,Read*6,Bash*2 mark=E07
原因找到了：PDF 用的是 UTC，不是商户的时区。顺着日期往下查，同样的问题还有两处。

**1. PDF**：`api/internal/invoice/pdf/render.go`

```go
issued := inv.IssuedAt.UTC().Format("2006-01-02")
due := inv.DueAt.UTC().Format("2006-01-02")
```

`IssuedAt` 存的是 `timestamptz`，取出来格式化前转成了 UTC。悉尼现在是 UTC+11（夏令时），当地上午 11 点之前开的发票，UTC 还是前一天，PDF 上就早一天。后台页面是对的，因为前端用浏览器的时区显示。

**2. 邮件**：`api/internal/invoice/email.go` 里给客户发发票邮件，正文“到期日：{{due}}”也是 `inv.DueAt.UTC().Format(...)`，问题一样。

**3. 到期日的计算**：`api/internal/invoice/due.go`

```go
func dueAt(issued time.Time, terms int) time.Time {
    d := issued.UTC().Truncate(24 * time.Hour)
    return d.AddDate(0, 0, terms)
}
```

先按 UTC 截到当天零点，再加账期天数。对东边的时区，这个“当天”可能是当地的前一天，所以到期日本身就早了一天，不只是显示问题。

**商户时区**：`merchants.timezone` 字段早就有（IANA 名字，比如 `Australia/Sydney`），目前只有前端在用，后端没有任何地方读它。

**影响面**：
- 商户时区在 UTC 以东的（我们大部分商户在 `Asia/Shanghai`，UTC+8），当地早上 8 点之前开的发票都会受影响。查了一下种子数据的分布，生产上的比例要另查，估计不小，只是之前没人注意。
- 西边的时区反过来，可能晚一天。
- 到期日早一天，会让逾期提醒早一天：`worker/reminder/job.go` 判断逾期用的是 `due_at < now()`，到期日早了，提醒就提前一天发。

**测试**：`due_test.go` 只测了 UTC 的情况，`render_test.go` 只比对版面，不看日期。

%% D4 客户列表接口加标签筛选（已做完）
@@ user
客户列表接口加一个按标签筛选的参数，`GET /v1/customers?tag=vip`，可以传多个 `tag`，要同时满足。标签已经存在 `customer_tags` 表里了。

@@ assistant tools=Read*4,Edit*5,Bash*3
做完了。

**改动**
1. `api/openapi.yaml`：`GET /v1/customers` 加查询参数 `tag`（数组，`style: form`，`explode: true`，所以写成 `?tag=vip&tag=wholesale`）。
2. `api/queries/customers.sql`：`ListCustomers` 加一个可选的标签条件。sqlc 不支持动态拼 SQL，所以用数组参数加 `cardinality` 判断：

   ```sql
   -- name: ListCustomers :many
   SELECT c.*
   FROM customers c
   WHERE c.merchant_id = @merchant_id
     AND (cardinality(@tags::text[]) = 0 OR c.id IN (
           SELECT ct.customer_id FROM customer_tags ct
           WHERE ct.tag = ANY(@tags::text[])
           GROUP BY ct.customer_id
           HAVING count(DISTINCT ct.tag) = cardinality(@tags::text[])))
     AND (@cursor::bigint = 0 OR c.id < @cursor::bigint)
   ORDER BY c.id DESC
   LIMIT @page_size;
   ```

   `HAVING count(DISTINCT ct.tag) = cardinality(...)` 保证多个标签同时满足。
3. `api/internal/customer/handler.go`：读 `r.URL.Query()["tag"]`，去重、去空、每个最长 32 字符、最多 10 个，超了返回 422。
4. 测试：`handler_test.go` 加了 4 个用例（不传、一个标签、两个标签同时满足、超过 10 个返回 422），`store` 的集成测试加了 1 个（testcontainers 里起 Postgres）。

**性能**：`customer_tags` 上已有 `(tag, customer_id)` 的索引。用种子数据（2 万客户、6 万条标签）看了执行计划，两个标签的查询走索引，3 毫秒。

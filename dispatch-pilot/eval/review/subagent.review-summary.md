## 规则决定

对照依据：spec #1 故事 33、34 和 Implementation Decisions「派出 agent 路由器」；SOURCES.md 的 subagent 附加约定；线上决策请求的档位描述 `dispatch-pilot/hooks/decision/effort.ts`（例如它把「编写测试」放在 high，subagent-050 的理由引用的就是这条）。

**1. 主 agent 的指定只差一档就保留（subagent-069，影响 17 道 main-kept 题）：同意。**
spec 规定主 agent 的指定是「强提示，置信度高于门槛才推翻」。SOURCES 里的三条推翻条件（差两档；让 haiku 写代码或做判断；让 opus/fable 做只读汇报或机械工作）就是这句话的具体做法。只差一档、选择说得过去时，gold 用主 agent 的指定，更合适的模型放进 accept。这样评测对「尊重主 agent」和「高置信度改成更合适的模型」两种结果都给分，不会因为决策模型守规矩而扣分。同一 workflow 里有对照题：066（无指定，审 payments）判 opus；069（指定 sonnet，审 6 个路由的 admin）保留 sonnet、opus 可接受。两题互相印证。逐题审 main-kept 题时，只看是否触发这三条之一，没有一题触发。说明一点：推翻条件里的「只读」指只搜索、只汇报、不需要判断的工作，不是字面上的「不改代码」。014、020、089 都是只读，但需要判断，所以保留 opus 与规则不冲突。

**2. 用户点名的 effort 也不推翻（subagent-012）：与模型同等对待。**
spec 故事 33 只写了模型。但这条故事的原则是「我的明确要求优先」，没有理由只保护模型、不保护 effort。用户在本轮写出的 effort 就是唯一可接受档位。012 的答案本来就是这样（sonnet/low，effort 只收 low），答案不变；但它的理由还把这件事当作待定问题，所以记为 note，交给下游改理由并补 spec。

**3. 否定说法不算点名（subagent-058、011、005）。**
只有肯定说法（「用 X」「X 就够了」「派个 X」）才算用户点名。「别用 X」是约束：X 从 accept 里排除，其余交给决策模型，标签用 `priority:none`。只有否定的（058）不是点名；否定加肯定的（011「别用 opus，用 haiku」、005「一律用 sonnet，别用 haiku」），肯定的那个模型就是点名。三题的现有标注都符合这条。

**4. 模型名作为产品被提到，不是指令（subagent-038、021、023）。**
用户说的是被比较的产品、线上系统用的模型、旧代码由谁生成，都不是在给这个 agent 指定模型，按没有点名处理。对 100 题的 user_message 做了一次关键词扫描（haiku/sonnet/opus/fable/模型），命中的每一题都核对过。现有标签全部正确，没有第四个漏判或误判的例子。

**5. 点名的作用范围（057、085–087、098–100、005、013）。**
点名只管它描述的那一步。「调研那种活儿用 haiku」不管实现 agent（057）；「证明用 fable」不管提取状态机和跑 TLC（099、100）。「接下来一律」「这次所有 agent」管本轮全部派出的 agent（005、013）。087 核对过原文（「最后用 sonnet 跑测试修问题」），标 `priority:user`、gold 为 sonnet，正确。

**6. 隐含点名（subagent-059「用最便宜的模型」）：维持 `priority:none`。**
mod 识别点名只认字面上的模型名，所以这题不算点名。但用户的意图明确，accept 只收 haiku，评分结果与当作点名一样，不需要改标签。

**7. 076（haiku 在 staging 上真正写入 4000 万行）：同意保留。**
停止条件已经给定（差异超过 0.1% 就停），核对方法也已给定（抽 200 行与 ledger 比对）。环境是 staging，操作可以恢复。这不属于「让 haiku 写代码或做判断」。accept 已经收了 sonnet 的 low 和 medium，所以决策模型升到 sonnet 也算对。074、075、076 三题是同一流程的梯度（只读统计 → 写脚本 → 执行），不单独给 076 升档。

## 需要跟进的备注

- **subagent-012**：答案不变。需要做两件事：(1) 把 rationale 里「实现时需要决定是否像模型一样直接采用」改成确定的说法；(2) spec #1 故事 33 和派出 agent 路由器（#6）补一条：用户点名的 effort 也不推翻，识别方式与模型点名相同。
- **评分口径（不属于单题，给 #15 的实现者）**：`accept.effort` 是所有模型共用的一组档位，没有按模型分开。所以 accept 同时有两个模型时，另一个模型配任一档位都算对，例如 089 的 opus/low、029 的 sonnet/xhigh。我逐题看过，目前的组合都说得通。以后新增题时要留意：这种双模型 accept 会不会放进不合理的组合。
- **SOURCES.md 的措辞**：建议把「让 opus/fable 做只读或机械工作」改成「做只需汇报、不需判断的只读工作或机械工作」，免得以后被理解成「凡是不改代码的都要推翻」，与 014、020、089 冲突。

## 规则决定

**1. 标注口径：标「下一段工作」需要的档位（midturn-087）。**
gold 标的是从这一步起、到 spec 规定的下一次重判之前（或这一轮结束之前）这段工作需要的档位。spec 规定的重判时机包括：每 N 步；失败满 M 次；派出 agent、启动 Workflow、加载 skill。不按剩余全部工作标：判断结果会一直生效到下一次重判，如果按剩余全部工作标，每次重判都会偏高，中途降档就没有意义了。也不只看严格意义上的一步：结果会持续 N 步，只看一步会低估。理由里如果写了「之后会在 X 时重判」，X 必须在上面的触发条件里。后台 agent 返回结果不在其中，所以 087 的理由需要改。

**2. 失败满 2 次的题：gold 标内容上的理想档位，accept 补上强制升档的下限（006、017、051、053、056、057）。**
按默认配置（升一档，M=2），这时的生产请求会带「卡住」标记，代码也会把结果抬到至少当前档 +1。所以如果理想档位不高于当前档 +1，模型答理想档位和答当前档 +1，在生产里的效果完全相同。这种情况下 accept 应该包含当前档 +1。否则调提示词时会把模型往「忽略卡住标记」的方向推，伤害真正卡住的题。六题里只有 006 需要改（理想档位 medium 就是当前档）。其余五题的 gold 本来就不低于当前档 +1，也都不接受保持当前档，保持原样。

**3. 强制升档到上限后（053）：上限不改变理想档位，按内容判断。**
counts 里没有强制升档次数，决策模型看不到上限是否已到，所以 gold 只能按内容定。053 按内容就是 max（xhigh 下多轮修复都失败，又牵涉支付回调），只接受 max 成立。如果其实没到上限，代码也会强制升到 max，结论一样。

**4. 安全、生产、不可逆这一类题怎么区分 max（032、047、048、050、067、069、071、072、088、096、100 等）。**
- 不可逆的高风险操作还在前面（072、048、100、067）：可以给 max。
- 漏洞还没堵上、影响严重（050：未带 token 的转账请求已经被接受，auth 等中间件可能同样放行）：可以给 max。
- 损害已经发生，剩下的是照清单处置（047）；或者影响有界、补救路径明确（088 伪造回调、096 读侧越权）：标 high 或 xhigh。050、088、096 的 accept 在 xhigh 处重叠，彼此不矛盾。
- 名字里带「安全」，但实际工作是机械的（064、068、084、091）：按工作本身打分。

## 需要跟进的备注

- **midturn-053**：理由有两处事实错误。一是 `counts.changes` 是档位变化次数，不是强制升档次数；二是 spec 里没有「+1 方式最高只到 xhigh」，从 xhigh 升一档就是 max。建议把标签 `forced-escalation-cap` 改为 `forced-escalation`。065 的理由也提到了强制升档，但那是轨迹里明写的（step [0] 写着「强制升档后」），不是从 counts 推出来的，所以不用改。
- **midturn-087**：理由说「结果返回时重判」，这不是 spec 的重判触发条件。建议改成依靠每 N 步的例行重判，并说明代码每次最多降一档，所以模型答 low 或 medium 在生产里的效果相同。
- **midturn-090**：题面有歧义。Workflow 在后台运行，题面没有交代主 agent 是等结果，还是先结束这一轮。按 087 的判断方式，这会影响 gold。建议在 assistant_text 里写明主 agent 会等结果再综合（像 081 那样写「前台运行」）。
- **spec 问题（需要用户拍板）**：计划内的失败目前都算失败，例如 TDD 的红灯（001、006）、`rg` 无匹配时退出码为 1（003）、`terraform plan -detailed-exitcode` 有变更时返回 2（005）、git pre-commit 钩子改写文件后中止提交（044）。006 这样的题会因此触发强制升档。要不要让强制升档参考决策模型对「是否真的卡住」的判断，还是维持纯计数？数据集已经按「代码照计数执行」标注了。
